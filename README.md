# Codex Harness

Первая версия автономного исполнителя: задача → спецификация и план → краткая
сводка → реализация → проверки → независимое ревью → приёмка человеком.
Сводка не требует ответа. Вопрос о существенной неопределённости останавливает
задачу. Исходная папка проекта остаётся неизменной.

Требования: macOS, Python 3.11+, Git, установленный и авторизованный Codex CLI.
Проверено с Codex CLI 0.166.0. Запуск контроллера внутри другой песочницы может
не позволить создать sandbox Codex; в таком случае запуск блокируется.

Для экспериментов есть [учебная площадка Taskboard](docs/playground.md):
отдельный проект, готовые задания, применение результата и сброс с архивированием.

## Работа через Tw

```sh
export PATH="/Users/twist/tmp/ai/harness-kit/bin:$PATH"
cd /Users/twist/tmp/ai/harness-kit/lab/taskboard
tw init
tw
```

`tw` — исполняемый launcher. Он открывает настоящий Codex со скиллом `tw` и
локальным MCP-контроллером этого проекта. Задачу можно описать обычным языком.
Чат читает исходники, а реализацию выполняет отдельный worker в рабочей копии.
Закрытие чата не останавливает worker. `tw status` показывает состояние,
`tw stop` запрашивает остановку worker с паузой активной задачи.

`tw init` требует Git-проект с исходным коммитом и команду проверок. Для
`tests/test*.py` она определяется автоматически; иначе укажите
`tw init --check 'команда проверок'`. Можно задать `--model MODEL` при первом
подключении. Уже настроенный check/model повторный init не перезаписывает.

Подключение сохраняет `AGENTS.md` и устанавливает свой skill в
`.agents/skills/tw/`. Чужой skill с таким именем или изменённый установленный
skill не перезаписывается. Существующие задачи сохраняются. Эти инструкции
можно позднее закоммитить после разрешения пользователя; init коммитов не делает.
Настройки shell, глобальные skills и config.toml не меняются. Команда export
выше действует только в текущем терминале; для другого терминала повторите её.

Сессия проходит canary-проверку перед запуском, получает исходный проект только
на чтение, без сети shell, секретов, сторонних MCP, приложений и browser tools.
MCP Tw ограничен одним проектом и не принимает произвольные команды или пути.
Приёмка и grants не доступны модели: человек принимает работу командой
`tw accept TASK-NNN --confirm TASK-NNN` в отдельном терминале.

Если MCP не запускается или нельзя проверить его изоляцию, Tw не запускает
обычный незащищённый чат вместо него. При `tw: command not found` используйте
абсолютный путь `/Users/twist/tmp/ai/harness-kit/bin/tw` или повторите export PATH.

## Низкоуровневый CLI

Из папки harness-kit:

```sh
python3 bin/harness --project /absolute/path/to/project init --check 'python3 -m unittest discover -s tests'
python3 bin/harness --project /absolute/path/to/project doctor
python3 bin/harness --project /absolute/path/to/project add 'Описание задачи и ожидаемого результата'
python3 bin/harness --project /absolute/path/to/project run TASK-001
```

`init` запускается в корне Git-проекта с хотя бы одним коммитом. Он сохраняет
команду проверок, не исполняет её и не меняет глобальные настройки Codex.
Команда check задаётся человеком, разбирается как argv, без shell-подстановок.
Для составных проверок используйте скрипт проекта. Модель можно задать через
`init --model MODEL`; без этого используется стандартный выбор Codex.

Рабочая копия создаётся из HEAD. Незакоммиченные изменения и неотслеживаемые
файлы исходного проекта в неё не попадают. Это безопасный экспорт обычных
отслеживаемых файлов, пока без собственной Git-ветки. Скрытые файлы, env,
известные имена секретов, символьные ссылки и submodules не экспортируются.

## Управление

Во всех примерах можно добавить `--project PATH` **перед** названием команды.

```sh
python3 bin/harness status
python3 bin/harness show TASK-001
python3 bin/harness pause TASK-001
python3 bin/harness resume TASK-001
python3 bin/harness answer TASK-001 'Ответ на вопрос'
python3 bin/harness worker
python3 bin/harness worker --once
python3 bin/harness accept TASK-001 --confirm TASK-001
```

`worker` последовательно обрабатывает очередь и возвращается к задачам после
лимитов. Для длительной работы оставьте его в tmux или другом устойчивом
терминале. Автозапуск после перезагрузки пока не устанавливается. `--once`
делает один обход очереди. `resume` возвращает задачу в очередь; для немедленного
продолжения вызовите `run`. Ответ также возвращает задачу в очередь.

`pause` останавливает текущий subprocess и оставляет этап для продолжения.
Ctrl-C и SIGTERM сохраняют паузу. После аварийного завершения контроллер
проверяет запись активного subprocess: пока тот жив, повторный запуск блокируется,
чтобы не было двух исполнителей одной задачи. Не удаляйте эту запись без проверки.

`accept` фиксирует приёмку и проверяет, что результат не изменился после ревью.
В новых проектах команда создаёт коммит результата и сливает его в настроенную
основную ветку. Сначала изучите preview, diff, проверки и отчёт
ревьюера. Для старых проектов это определяется настройками ниже. Patch текстовый;
изменения режима файлов описаны в `changes.json`, бинарные изменения блокируются.

## Решение по результату

Результат в review/done можно принять, вернуть с замечаниями или окончательно
отклонить. Это операторские действия, агентскому MCP они не доступны:

```sh
python3 bin/tw accept TASK-001 --confirm TASK-001
python3 bin/tw request-changes TASK-001 'Что нужно исправить'
python3 bin/tw reject TASK-001 --reason 'Почему отклоняем' --confirm TASK-001
```

Доработка возвращается в очередь с тем же планом;
существующий worker продолжит её, либо используйте worker/run. Финальное
отклонение сохраняет историю, документы и рабочую копию; resume не оживляет
rejected. Предпросмотр отклонённой задачи отключается. Эти действия доступны
также во встроенных доверенных формах веб-панели.

## Режимы согласования

Новые задачи имеют два режима: `auto` (по умолчанию) и `approve-plan`.
Приоритет и срочность не отменяют согласование. Можно потребовать его явно:

```sh
python3 bin/tw add 'Описание задачи' --approval approve-plan
python3 bin/tw show TASK-001
python3 bin/tw approve-plan TASK-001 --version SHA256 --confirm TASK-001
python3 bin/tw revise-plan TASK-001 'Уточни границы и проверки'
```

Вместо SHA256 укажите полную версию из show или summary.txt. Утверждение
возвращает задачу в очередь; внешний worker продолжит её, либо используйте run.
Возврат с замечаниями повторяет планирование до начала реализации.
Утверждение плана не означает приёмку результата или выдачу прав доступа.

Планировщик оценивает риск и объём. Высокий/неизвестный риск, большой/неизвестный
объём, критичные пути и явное требование в запросе повышают auto до согласования.
Оценка риска эвристическая; для обязательной остановки задавайте approve-plan.
Контроллер сохраняет документы и версию, затем ждёт в awaiting_approval.
answer/resume/run не обходят ожидание; изменённые документы блокируют исполнение.
MCP может поставить задачу с approval=approve-plan и показать её версию,
но не может утвердить план за человека. Веб-кнопок пока нет.

Старые задачи сохраняют прежнюю семантику. Работающий worker не обновляется
автоматически; новые правила действуют в новых процессах. Декомпозиция пока
представлена шагами Markdown-плана, без дочерних задач и зависимостей.

## Файлы состояния

```text
.harness/
  config.json
  state.sqlite
  tasks/TASK-001/
    workspace/
    specification.md
    plan.md
    summary.txt
    plan-01.json
    implement-01.json
    review-01.json
    review.md
    check.log
    changes.patch
    changes.json
```

SQLite хранит исходный запрос, этапы, попытки, вопросы, ответы и события.
`*.jsonl` содержит вывод Codex, `*.request.txt` — переданный агенту контекст.
Не передавайте секреты в текст задачи или ответа: эти данные сохраняются.
Добавьте `.harness/` в ignore подключаемого проекта перед собственными коммитами.
В этом репозитории правило уже добавлено.

## Гварды

Защита проверяется на безопасных временных canary-файлах перед каждым запуском.
Она запрещает чтение скрытых файлов, env, ключей, credentials, файлов вне
рабочей копии, запись наружу и сеть дочерних команд. SSH/SCP/SFTP-соединения
блокируются закрытой сетью; сам запуск бинарника, например `ssh -V`, не запрещён.
Унаследованные переменные с токенами и
SSH agent не передаются. Проверки проекта работают в той же песочнице.
Планировщик и ревьюер получают доступ к рабочей копии только на чтение.

Codex запускается отдельно, без пользовательского config.toml, плагинов,
приложений, browser/computer use, image generation и lifecycle hooks.
Собственные shell-команды не могут запросить эскалацию. Транспорт Codex к
OpenAI и внутреннее использование авторизации самим CLI остаются доступны;
авторизационные файлы недоступны командам агента.

В этой версии разрешения **не выдаются автоматически вообще**. Агент сохраняет
запрос: конкретное действие, ресурс, причина, срок. Человек может выполнить
действие сам после собственного решения и передать безопасный результат через
`answer`. Даже ответ «разрешаю» не меняет профиль доступа. Одноразовые технически
ограниченные разрешения добавим отдельной итерацией; общего переключателя
«открыть всё» нет.

Правила по именам файлов не обнаруживают секрет, встроенный в обычный исходник.
Контроллер рассчитывает на явно заданную команду проверок и чистый исходный
коммит. Новые зависимости не устанавливаются; окружение не поднимается
автоматически. Разрешение обычных скрытых конфигов, toolchain и локальных
тестовых сервисов потребует узких политик в следующей итерации.

Точное оставшееся количество запросов не показывается. Пока распознаётся отказ
из-за лимита, задача сохраняет этап и назначает повтор через 5 минут, затем с
увеличением интервала до 5 часов. Точное время сброса ещё не извлекается.
При неожиданной ошибке или после трёх попыток этапа задача блокируется с причиной.

## Проверка реализации

```sh
python3 -m unittest discover -s tests/codex -v
python3 -c 'from harness.security import doctor; print(doctor("codex"))'
```

Первый набор не вызывает модель. Второй проверяет реальную песочницу без
доступа к настоящим секретам и без запросов к модели. Отдельный
`python3 tests/codex/live_smoke.py` делает настоящий проход на временном учебном
проекте и расходует лимит Codex.
`python3 tests/codex/live_tw_smoke.py` проверяет также реальный чат Codex,
MCP-постановку задачи и продолжение внешнего worker после выхода из чата.

Старые `scripts/`, `hooks/`, `skills/`, `.claude-plugin/`, `ROADMAP.md` и
`docs/workflow.md` описывают прежний Claude harness и не подключены к новому
исполнителю. Текущая спецификация: [docs/specs/2026-11-02-codex-harness.md](docs/specs/2026-11-02-codex-harness.md).

Основания для адаптера: [permissions](https://learn.chatgpt.com/docs/permissions),
[developer commands](https://learn.chatgpt.com/docs/developer-commands?surface=cli).

## Локальная веб-панель tw-web

Операторский launcher — bin/tw-web; frontend разрабатывается отдельной
задачей в соседнем проекте tw-web и обслуживается как проверенный статический
Next export. Контроллер не исполняет серверный код этого frontend.

```sh
tw-web
tw-web status
tw-web stop
```

Панель слушает 127.0.0.1:47831, подтверждения плана/приёмки/отклонения —
127.0.0.1:47832. Человеческие решения выполняются только после формы на
отдельном origin контроллера; агентский MCP этих полномочий не получает.
В браузере доступны задачи, причины ожидания, артефакты и история; действия
определяются текущим состоянием и версией контроллера. Изменяющие запросы
используют CSRF, revision и ключи идемпотентности, сохраняемые в SQLite.
Закрытие вкладки и остановка панели не останавливают worker.

Node toolchain для этой итерации подготовлен отдельно в harness-owned state:
версии/lockfile/runtime/dependency tree фиксируются хэшами. Проверки frontend
идут в отдельной сборочной копии с read-only зависимостями и закрытой сетью,
после canary. Это не общее автоматическое npm-окружение для любых проектов.

Новые задачи берут snapshot из HEAD проекта, включая ранее слитые результаты.
До приёмки изменения находятся в отдельной рабочей копии и доступны через
поддерживаемый preview; основная копия сохраняет принятую версию.

### Продолжение проверенного результата

`bin/harness --project /path/to/project prepare-baseline TASK-003 --from-task TASK-002`
подготавливает остановленную задачу на этапе plan из проверенного завершённого
результата того же проекта. Исходная копия сохраняется, источник не принимается
и не применяется. Продолжение через answer/resume; diff новой задачи считается
от переданной основы, происхождение передаётся ревьюеру. Незавершённая подготовка,
изменённые исходники или локальные правки целевой копии блокируют операцию.

Опция контроллера `quota_guard: true` включает проверку пятичасового лимита через
Codex app-server: новые этапы останавливаются при 90%, активные — при 94%
(проверка каждые 15 секунд), с ожиданием до сброса + 60 секунд. Неизвестный лимит
блокирует новые вызовы. После сброса нужна свежая проверка. Guard контролирует
этот runner; общий расход других сессий всё равно входит в лимит аккаунта.

### Worktree, предпросмотр и коммит после приёмки

Новые проекты получают `task_worktrees: true`, `commit_after_accept: true`,
`apply_after_accept: true` и `integration_branch` с текущей веткой проекта.
Контроллер держит ветку `tw/TASK-NNN` в worktree того же репозитория. Агент
работает в безопасной копии исходников без Git-метаданных; после приёмки
контроллер переносит точный проверенный результат в worktree и коммитит.
При включённом `apply_after_accept` приёмка также сливает результат в основную
копию. Требуются нужная ветка и чистое рабочее дерево. При конфликте merge
отменяется, причина сохраняется в `integration_error`: принятие не выдаётся
за успешное применение. После устранения причины оператор может повторить
`tw apply-result TASK-003`. Повтор не создаёт дубликат коммита/merge.
`tw commit-result TASK-003` создаёт только коммит. Для самой панели проверенный
export принятой задачи активируется по обычному адресу без замены worker.

```sh
tw preview TASK-003
```

Команда печатает отдельный loopback URL. Предпросмотр работает до приёмки,
следит за сохранёнными файлами и обновляет страницу после успешной пересборки.
Поддерживаются подготовленный Next toolchain и статический сайт с index.html
в корне рабочей копии. Для других runtime требуется отдельный адаптер.
Next собирается контроллером в проверенном sandbox без сети; установка новых
зависимостей для preview автоматически не выполняется. Последняя успешная
версия остаётся доступна при промежуточной ошибке, статус обновления виден
на странице. Валидация preview не подменяет итоговые проверки задачи.
Предпросмотр не имеет изменяющих API и полномочий приёмки; управление задачей
выполняется в основной панели. Платные вызовы агента для обновлений не нужны.

### Наблюдение в терминале и встроенные решения

`tw watch TASK-004` показывает текущий этап и события существующей задачи;
`--once` выводит один снимок. Ctrl+C закрывает наблюдение, не останавливая worker.
Status содержит worker.task_id и worker.observation; task.observation содержит
готовую quoted terminal_command, mode=events и interactive=false. Это просмотр,
а не интерактивное подключение к stdin агента.

Control содержит confirmation_widgets для разрешённых решений. Встроенная форма
на /confirm/embed обслуживается доверенным origin контроллера. Она принимает
один явный POST пользователя, проверяет одноразовый токен/версию/revision и
сообщает результат parent.postMessage только точному origin панели. UI проверяет
origin и source iframe, затем перечитывает состояние. Preview этих полномочий
не получает. Исходный текст задачи доступен как task.request.
