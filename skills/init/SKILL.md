Подключи рельсы tw к проекту в текущей рабочей директории. Пустая папка или новый проект — нормальный случай: рельсы подключаются до того, как появится код.

1. Корень проекта: ближайшая вверх директория с `package.json` или `.git`; если их нет — текущая директория. Ничего не создавай и не предлагай создать: ни `package.json`, ни `git init`, ни каркас проекта.
2. Команда тестов: если в `package.json` есть скрипт `test` (не заглушка `npm init`) — `npm test`. Если тестов нет — не спрашивай и поле `test` не пиши: hooks сами возьмут `npm test`, когда скрипт появится.
3. Команда проверок `check` — то, что Stop гоняет вместо одних тестов. Если в `package.json` есть скрипт `check` — поле не пиши, hooks возьмут `npm run check` сами. Иначе собери из существующих скриптов в таком порядке: `typecheck` (или `tsc`), `lint`, тесты — через `&&`, например `npm run typecheck && npm run lint && npm test`. Если кроме тестов ничего нет — поле не пиши. Скрипты и линтеры не добавляй.
4. Создай `.claude/tw.json`:

```json
{
  "test": "<команда тестов, если определена>",
  "check": "<команда проверок, если собрана>"
}
```

Проект на pnpm или yarn (`pnpm-lock.yaml`, `yarn.lock`) — добавь `verifyTools`: независимый проверяющий по умолчанию запускает только `npm` и `npx`, а без вывода команд пункты не засчитывает. По `Bash(<pm> <скрипт>:*)` на каждую часть `check`, плюс `Bash(<pm> exec vitest:*)` и `Bash(<pm> exec tsc:*)`.

Исполнитель бэклога работает в отдельном git worktree, и неотслеживаемых файлов там нет. Если в корне или в пакетах лежат файлы окружения (`.env`, `.env.local` — смотри только имена через `git ls-files --others --ignored --exclude-standard`, содержимое не читай) — спроси пользователя, нужны ли они проверкам; если да — `runCopy` с их путями.

Пустые поля не пиши; ничего не определилось — `{}`. Если файл уже есть — покажи его и спроси, перезаписывать ли.

5. Добавь строки `.claude/tw-state/` и `docs/backlog/` в `.gitignore` корня (бэклог — личный список задач, статусы пишет исполнитель; в git он мешал бы слиянию); нет файла — создай.
6. Докажи, что проверки умеют падать (пропусти, если команды нет). Запусти команду на чистом дереве и запомни результат. Затем для каждой части команды (типы, линтер, тесты) по очереди создай через Write временный файл-нарушение рядом с кодом (`src/tw-probe.ts` или аналог: `const n: number = "x"; export {}` для типов, неиспользуемая переменная для линтера, `expect(1).toBe(2)` в `tw-probe.test.ts` для тестов), запусти команду, убедись, что она упала с ненулевым кодом, удали файл. Часть, которая не упала, — не работает: так и напиши.
7. Песочница исполнителя: `command -v srt`. Нет — одной строкой: фоновый исполнитель (`/tw:run`) без неё не стартует, поставить — `npm i -g @anthropic-ai/sandbox-runtime`. Сам не ставь.
8. Сообщи коротко: что создано, какая команда проверок (или «появится вместе со скриптом test»), есть ли srt, результат на чистом дереве, какие части доказали падение, и что рельсы заработают после `/clear` или новой сессии. Дальше задачу не начинай.
