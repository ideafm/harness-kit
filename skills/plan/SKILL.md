# План по спецификации

Каждое своё сообщение пользователю, пока идёт этот этап, начинай с метки отдельной строкой: `**[tw · 2/5 план]**` при составлении плана, `**[tw · 3/5 исполнение · задача N из M]**` при исполнении. Этапы tw: 1/5 спека → 2/5 план → 3/5 исполнение → 4/5 проверка (её печатают hooks строками `tw ▸`) → 5/5 приёмка (`/tw:accept`).

Спецификация отвечает «что и когда готово». План отвечает «в каком порядке и чем докажем каждый шаг». Он же — ledger: по нему следующая сессия понимает, где остановились, без пересказа.

**До утверждённого плана не создавай ничего, кроме файла плана.**

## Процесс

1. Прочитай спецификацию и то, что уже есть в проекте.
2. Разбей работу на 2–7 задач. Задача — один проверяемый шаг: после неё можно запустить команду или посмотреть на факт и сказать «да/нет».
3. Каждый пункт «Готово, когда» спецификации должен закрываться хотя бы одной задачей. Пункт, который агент проверить не может (например, «посмотреть глазами»), — уходит в «Приёмку» с пометкой `[человек]`.
4. Запиши `docs/plans/ГГГГ-ММ-ДД-<тема>.md` строго по шаблону. Код в план не пиши — только что сделать, какие файлы трогаешь и чем проверить. Файл, которого нет ни в плане, ни в спецификации, scope-hook считает выходом за план.
5. Покажи путь и список задач одной строкой каждая, спроси: «Утверждаешь план?». После «да» поставь `**Статус:** в работе` и начинай с задачи 1.

## Шаблон

```markdown
# План: <тема>

**Спецификация:** docs/specs/<файл>.md
**Статус:** черновик

## Задачи

- [ ] 1. <что сделать> — `<файлы, которые задача создаёт или меняет>`
  Проверка: <команда или наблюдаемый факт>
  Закрывает: <пункт «Готово, когда» спецификации>

## Приёмка

- [ ] <пункт «Готово, когда» спецификации> — <чем проверено>

## Журнал
```

## Исполнение

- Задачи по порядку. `[x]` ставь только после того, как проверка задачи реально прошла, — не по ощущению.
- После каждой задачи — один пункт списка в «Журнал»: `- ГГГГ-ММ-ДД · задача N · что сделано · чем проверено`. Если отошёл от плана — допиши почему.
- План оказался неверным (задача не нужна, нужна новая, порядок другой) — сначала поправь план и запиши в журнал, потом делай.
- Все задачи и приёмка закрыты — `**Статус:** готов`. При остановке hook запустит независимого проверяющего: он сверит спецификацию с diff. Не подтвердил — верни `в работе`, сними `[x]` с неподтверждённой приёмки, доработай, запиши в журнал.
- После подтверждения не коммить и приёмку не закрывай: скажи пользователю, что готова карточка одобрения, и что её покажет `/tw:accept`. Решение о приёмке и коммите — за ним.
- Бросили работу — `**Статус:** брошен` и причина в журнале.

## Отговорки

| Мысль | Реальность |
|---|---|
| «Задача маленькая, план не нужен» | Тогда в плане будет 2 задачи. Без плана следующая сессия не знает, что сделано. |
| «Распишу подробно, с кодом» | План читают человек и hooks. Код живёт в коде. |
| «Отмечу задачу, проверю потом» | Отметка без проверки — ложь в ledger. |
| «Тесты зелёные — закоммичу сразу» | Коммит — только после «да» пользователя. |
| «Есть другой skill планирования» | В tw-проекте план должен лежать в docs/plans/ по этому шаблону — его читают hooks. |

## Красные флаги — остановись

- Создаёшь файл, который не план, до «да».
- У задачи нет строки «Проверка».
- Пункт «Готово, когда» спецификации не закрыт ни одной задачей.
- Задача меняет файл, который в «Не трогаем» спецификации стоит путём в обратных кавычках: hook заблокирует правку. Не утверждай план — спроси пользователя, поправить спеку или задачу.
- Поставил `[x]` и не запускал проверку.
