# Спецификация до работы

Каждое своё сообщение пользователю, пока идёт этот этап, начинай с метки отдельной строкой: `**[tw · 1/5 спека]**`. Этапы tw: 1/5 спека → 2/5 план → 3/5 исполнение → 4/5 проверка (её печатают hooks строками `tw ▸`) → 5/5 приёмка (`/tw:accept`).

Задача одной фразой — это развилки, которые ты закроешь догадками. Догадка, которую пользователь не видел, — это результат «не тот». Этап закрывает развилки вопросами и оставляет файл, по которому потом принимают работу.

**До утверждённой спецификации не создавай ничего, кроме файла спецификации.** Ни кода, ни макетов, ни «черновика, чтобы показать».

## Процесс

1. Посмотри, что уже есть в проекте (стек, похожие страницы, README) — не спрашивай то, что можно прочитать.
2. Про себя выпиши развилки: всё, что пришлось бы угадать. Отсортируй по цене ошибки.
3. Задавай **один вопрос за сообщение**, самый дорогой первым. Формулируй как проверку догадки: «Предполагаю X, потому что Y — так?». Хватит 3–5 вопросов; торопят — задай 2 самых дорогих. Если есть инструмент `AskUserQuestion` — задавай вопрос через него: 2–4 варианта, твоя догадка первой с пометкой «(рекомендую)», в описании варианта — что из него следует; свой вариант пользователь впишет сам в «Other». Нет инструмента (headless) — тот же вопрос текстом с нумерованными вариантами и строкой «или напиши свой».
4. Если пользователь говорит «решай сам» — реши, но в спецификации пометь это `[допущение]`.
5. Запиши `docs/specs/ГГГГ-ММ-ДД-<тема>.md` строго по шаблону ниже.
6. Покажи путь и 3–5 строк сути, спроси: «Утверждаешь?». Дальше — только после «да».
7. После «да» вызови skill `tw:plan`.

## Шаблон

```markdown
# <Название>

**Цель:** зачем это нужно, какой эффект ждём.

**Результат:** что конкретно появится — файлы, страницы, отчёт, сколько вариантов, в каком виде.

**Готово, когда:** проверяемые условия, по которым пользователь примет работу.

**Не трогаем:** что менять нельзя — пути и папки в обратных кавычках (`src/legacy/`, `package.json`): по ним hook ловит лишние правки, и любой путь в кавычках запрещает файл целиком. Часть файла (функцию, список) описывай словами без пути и без кавычек: «список services в catalog.ts не меняем».

**Не цель:** что сознательно не делаем сейчас.

**Входные данные:** что есть (ссылки, тексты, данные), чего не хватает.

**Допущения:** всё, что решено без пользователя, — каждое с пометкой `[допущение]`.
```

Раздел без содержания не удаляй — пиши «нет» или «не обсуждали», чтобы пробел был виден. Между разделами — пустая строка, список внутри раздела — тоже после пустой строки.

## Отговорки

| Мысль | Реальность |
|---|---|
| «Срочно, некогда спрашивать» | Два вопроса — минута. Переделка «не того» — часы. Срочность сокращает число вопросов, не убирает их. |
| «Поставлю заглушки, потом заменят» | Заглушки в названии, текстах и данных — это догадки о продукте. Спроси или пометь `[допущение]` в спецификации. |
| «Задача и так понятна» | Выпиши развилки. Если их ноль — пиши спецификацию сразу и всё равно проси утвердить. |
| «Сделаю черновик — так быстрее обсуждать» | Черновик закрепляет твои догадки. Сначала спецификация. |
| «Спрошу в конце, что поменять» | Вопрос после работы — это переделка, а не уточнение. |

## Красные флаги — остановись

- Создаёшь файл, который не спецификация, до слова «да».
- Придумал название, цены, тексты, данные и не спросил.
- Задал больше одного вопроса в сообщении.
- В спецификации нет «Готово, когда».
