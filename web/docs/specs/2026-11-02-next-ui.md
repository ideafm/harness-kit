# tw-web: Next.js и shadcn/ui

**Режим:** approve-plan.
**Статус:** подготовка через harness, реализация не начата.

Пользователь посмотрел TASK-001 и попросил приятный интерфейс на Next.js
с готовым UI-kit. Выбран Next.js App Router + TypeScript + Tailwind CSS +
shadcn/ui. Сам контроллер остаётся Python-сервисом в harness-kit.
Существующая TASK-001 остаётся на приёмке; редизайн не означает её принятие.

## Интерфейс

Компактная рабочая панель: sidebar проектов, блок «Требует решения», таблица
задач, карточка выбранной задачи. Светлый нейтральный фон, чёткая типографика,
спокойный акцент, цветовые статусы. Без декоративных графиков и fake-данных.

В карточке сначала показываются результат, текущее ожидание и действия.
Исходный запрос свёрнут по умолчанию. Спецификация, план, изменения, проверки,
ревью и события доступны вкладками; длинный код прокручивается внутри панели.
Этап и состояние различаются. Актуальность данных, ошибки и недоступные
действия отображаются явно. На телефоне список и карточка становятся отдельными
представлениями; действия остаются доступными без горизонтальной прокрутки.

Использовать настоящие компоненты shadcn/ui: Sidebar, Table, Badge, Tabs,
Sheet, Dialog/AlertDialog, Button, Textarea, Skeleton, ScrollArea, уведомления.
Формы и диалоги доступны с клавиатуры. Текст задач, логов и diff не выполняется
как HTML. Системные локальные шрифты; при сборке нет скачивания Google Fonts.

## Цикл действий

Одна команда tw-web открывает панель, порт 47831 сохраняется. Постановка задачи,
режим auto/approve-plan, пауза/продолжение, вопросы и ответы, просмотр документов
и результата выполняются через интерфейс. Результат предлагает три решения:
«Принять», «На доработку» с замечаниями, «Отклонить» с причиной.
Приёмка и применение — отдельные действия; если безопасного применения нет,
кнопка недоступна с точным объяснением. Автокоммиты не добавляются.

Планы утверждаются по точной версии. Приёмка и окончательное отклонение требуют
явного подтверждения. Повторный запрос не дублирует действие. Preview чужого
результата изолирован от операторского origin и не получает CSRF/полномочия.

## Граница с контроллером

Next — интерфейс и узкий BFF. Он не открывает SQLite, не меняет переходы задач
и не исполняет произвольные команды/пути. Операторские методы, подтверждения,
CAS и идемпотентность реализуются отдельно в harness-kit. Агентский MCP
по-прежнему не утверждает план, не принимает и не отклоняет работу.
Кнопки без готового контроллерного действия не имитируют успех.

## Node toolchain как отдельная предпосылка

Текущий sandbox разрешает только Python-проверки, закрывает сеть, скрытые пути
и не экспортирует node_modules. Нельзя запускать npm/Next в unrestricted mode
или подмешивать пользовательские .npmrc/.env/ключи ради удобства.

Контроллер должен заранее подготовить проверенный Node runtime и фиксированные
зависимости по lockfile, исключить install scripts по умолчанию, сохранить хэши
и дать агенту только необходимое чтение. Проверки выполняются отдельно в
проверенном sandbox и выделенной сборочной копии, чтобы generated-файлы не
попадали в diff исходников. Сеть worker остаётся закрытой. Источники и хэши
receipt должны относиться к проверяемому дереву.

Видимый Node обнаружен по /opt/homebrew/Cellar/node/25.9.0_2/bin/node; это только
кандидат для отдельной проверки. Node из скрытого ~/.nvm не используется.
Новые npm-зависимости пока не устанавливались. distDir можно направить в build,
но это само по себе не решает проблему изоляции зависимостей и generated-файлов.

Нужны TypeScript check, component/interaction tests с подставленным API,
production build, Python-тесты контроллера и local HTTP smoke. Browser QA
нового интерфейса выполняется после отдельного разрешения; старое разрешение
на скриншот текущей панели не распространяется автоматически на новые ресурсы.
