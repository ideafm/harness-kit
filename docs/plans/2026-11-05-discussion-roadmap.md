## 1. Достоверный результат на постоянном адресе

Приоритет: сначала разобрать отсутствие предпросмотра TASK-007. Она остаётся
непринятой; сообщение об отсутствии адреса не означает публикацию на :47831.
Показать конкретную причину и возможность повторить запуск. Перед приёмкой
доступны результат, сводка изменений, проверки и ограничения. Отсутствие
результата не должно маскироваться статусом готовности.

Целевой сценарий: пользователь запускает проект, например в Docker, получает
localhost:3000, ставит задачу и после «готово» проверяет её на том же адресе.
Tw управляет подключением рабочей копии задачи, готовностью, сборкой и
перезапуском; пользователь не переключает ветки и порты вручную. Просмотр
охватывает приложение целиком, включая backend, когда он есть.

Ветка сама по себе не переключает файлы работающего приложения. Конкретный
механизм Docker ещё нужно спроектировать: mount/worktree, пересборка образа
или переключение сервиса за постоянным адресом. Это обсуждение не разрешает
доступ к Docker socket, env, секретам или реальным данным. Требования изоляции
и проверяемого владения ресурсами остаются обязательными.

Для одного агента используется один постоянный адрес. На ручной приёмке
результат закреплён за задачей. По уточнению 2026-11-06 зависимые задачи ждут,
независимые продолжаются в собственных ветках. Просмотр ожидающей приёмки
задачи не переключается автоматически; для проверки другой версии потребуется
явное переключение либо дополнительный адрес. Детали этого UX ещё спроектировать.
При автоприёмке очередь продолжается; утром адрес показывает накопленный
принятый результат. Всегда видно, какая задача и версия сейчас открыта.
При ошибке нового запуска сохраняется последняя рабочая версия с явным
предупреждением о её несоответствии текущей задаче. Для параллельной работы
допускаются дополнительные адреса.

Основа static/Next и CLI уже есть. Не завершены восстановление last-good после
перезапуска, web-управление и миграция старых preview. Общий Docker/runtime
ещё не реализован. Постоянный проектный просмотр :43664 и панель :47831
сейчас являются разными сервисами; целевой порт 3000 — пример, не обещание
уже выполненной перенастройки.

Проверка этапа: две последовательные задачи на одном адресе, точная версия,
ошибка сборки, перезапуск, ожидание человека, отклонение и сохранность main.

## 2. Понятная приёмка и спокойный интерфейс

- «Доработать» открывает модалку с одним полем замечаний.
- «Отклонить» требует обычного подтверждения без ввода номера задачи
  и обязательного комментария.
- «Принять» объясняет последующий commit/merge и подтверждает действие.
- Блок списка задач шире; компактная строка содержит номер, статус и превью
  названия. Ориентир — около 20 задач на обычном десктопном экране.
- Колонки выровнены сверху; переключение задачи не двигает список.
- SSE доставляет изменения; команды остаются HTTP-запросами. Обновляются
  затронутые данные без моргания, сброса прокрутки, фокуса и введённого текста.
  При переподключении выполняется сверка актуального состояния.

Проверка этапа: модалки и подтверждения, 20 строк, переключение задач,
обновление при вводе текста, разрыв и восстановление SSE без потери состояния.

## 3. Бэклог и ночная очередь

При создании явный выбор: «В бэклог» без автоматического старта либо
«В очередь» с разрешением начать при освобождении агента. Из бэклога можно
выбрать несколько задач галочками, задать порядок и запустить группу.
Сначала последовательное выполнение одним агентом.

Учитывать зависимости: заблокированная задача останавливает зависимые,
независимые продолжаются в собственных ветках. Ручная приёмка закрепляет
постоянный просмотр и приостанавливает зависимые задачи до решения. Утренний отчёт:
выполнено, автоматически принято, требуется человек, причина остановки.

Проверка этапа: создание без старта, групповой запуск, порядок, зависимости,
двойной запуск, восстановление очереди после остановки и соблюдение лимитов.

## 4. Автоприёмка после независимого ревью и QA

Согласована настройка задачи «Принять автоматически после проверок», включённая
по умолчанию для новых задач после внедрения механизма. Это будущая политика,
она не разрешает сейчас принять TASK-007 или другие существующие результаты.

Условия: обязательные проверки успешны, независимый ревьюер и QA одобрили
результат, замечания закрыты, объединённый результат проверен на актуальной
основной ветке. Разрешение привязано к конкретной версии результата;
изменение кода требует повторных проверок. Решение исполняет контроллер.

Руководитель может заблокировать merge с конкретной причиной и запросить
человека, но не может обойти обязательные проверки или расширить доступ.
Неоднозначные требования, спорное визуальное решение и последствия вне Git
могут требовать человека. Git-откат не отменяет миграции данных и внешние
действия; публикация, секреты и реальные данные требуют отдельных разрешений.

Это изменяет прежнее требование исключительно ручной приёмки как продуктовую
цель. Действующий механизм остаётся прежним до реализации и проверки политики.

Проверка этапа: автоматический commit/merge только проверенной версии,
отрицательное ревью/QA, veto руководителя, stale receipt, конфликт интеграции,
повтор операции и отсутствие расширения прав.

## 6. Пилотный проект

Пилот выбран: приложение собирает вакансии по заданным фильтрам и при открытии
показывает ещё не просмотренные. Просмотр означает открытие вакансии,
а не её появление в списке. Источники, фильтры, стек, детали поведения
и объём первой версии обсудить при планировании проекта, не уточнять сейчас.
tutor-saas отменён. Выбор пилота не означает разрешение начать реализацию
или обращаться к внешним источникам и защищённым ресурсам. На пилоте проверить
полный цикл: запуск → бэклог → ночная очередь → review/QA → приёмка →
результат на постоянном адресе → утренний отчёт.

### Обсуждение проекта при tw init

Включить в roadmap обсуждение проекта «на берегу» при инициализации Tw.
До детального планирования задач должна появиться общая канва: для кого
приложение, какую проблему решает, основной сценарий, границы первой версии,
ограничения и признаки успешного результата. Для существующего проекта
учитывать уже имеющийся контекст и не заставлять проходить опрос заново.

Сохранять согласованную канву как контекст проекта для руководителя,
разработчика, ревьюера и QA. Неизвестное отмечать открытыми вопросами,
не выдумывать ответы. Обсуждение можно продолжить позже; инициализация
сама не запускает реализацию или очередь. Детальное планирование —
следующий отдельный шаг. Конкретный формат диалога ещё спроектировать.

Проверка при реализации: новый и существующий проект, сохранение и продолжение
обсуждения, открытые вопросы, отсутствие автоматического запуска задач.

## 7. Дополнения после знакомства с Paperclip

Согласованы к включению в ближайший roadmap три пункта ниже. Paperclip
используется как источник продуктовых идей; его реализация не проверялась,
установка или перенос кода не планировались.

### 7.1. Единый раздел «Нужно ваше решение»

Собрать приёмки, вопросы, блокировки, требующие человека, и запросы разрешений
в одном месте. Каждая запись содержит задачу, конкретную причину остановки,
варианты решения, рекомендацию и ссылки на доказательства. Технические
блокировки без действия пользователя показывать в статусе задачи, не засоряя
список решений. После решения запись остаётся в истории.

Связать с этапом 2 интерфейса и этапом 4 автоприёмки. Решение привязано
к актуальной версии задачи; повторный или устаревший ответ не выполняет
операцию дважды. Запрос разрешения показывает точный ресурс и действие.

Проверка: все виды обращений в одном списке, переход к результату, закрытие
и история, устаревшее решение, отсутствие дубликатов после переподключения.

Источник: https://docs.paperclip.ing/guides/day-to-day/approvals/

### 7.2. Критерии готовности до начала реализации

При постановке агент формулирует проверяемые критерии результата на основании
запроса. Существенная неоднозначность требует уточнения. Разработчик, независимый
ревьюер и QA работают с одной версией критериев; перед приёмкой видно, чем
подтверждён каждый пункт: тест, сценарий, скриншот или проверяемая ссылка.
Самоотчёт разработчика не заменяет независимую проверку.

Связать с созданием задач в этапе 3 и условиями этапа 4. Изменение критериев
сохраняется в истории и не может незаметно оправдать неполный результат.

Проверка: критерии сохранены до реализации, связаны с доказательствами,
пропущенный критерий блокирует автоприёмку, изменение не теряет историю.

Источник: https://paperclip.ing/product/tasks/

### 7.3. Контроль зависаний и восстановление ночной очереди

Контроллер различает работу агента, ожидание инструмента, лимит, потерю процесса
и повторение одной проблемы. Проверка жизнеспособности сама не вызывает модель.
Долгая операция без новых сообщений не считается зависшей без дополнительных
признаков; правила таймаутов задаются по этапам.

Временный сбой допускает ограниченное восстановление. Счётчик попыток переживает
перезапуск; после исчерпания показываются точная причина, последний сохранённый
этап и следующее действие. Сохраняются подтверждённые результаты этапов.
Возобновление не дублирует выполнение и не обходит паузу пользователя, лимиты,
ручную приёмку или зависимости.

Связать с этапом 3 очереди и существующим functional-work-packages 2.6.
Продолжение разрешённой работы запускается событиями завершения, освобождения
агента и снятия зависимости. Обычный комментарий не снимает явную паузу.
Утренний отчёт опирается на сохранённую историю, а не реконструкцию моделью.

Проверка: потеря процесса, зависший инструмент, длительная исправная операция,
исчерпание повторов, перезапуск контроллера, отсутствие двойного запуска
и соблюдение ручной паузы/лимитов.

Источник: https://paperclip.ing/product/heartbeats/

## 8. Бэклог UI/UX после изучения Paperclip

Статус: согласовано сохранить в бэклог, без автоматического запуска и без
изменения ближайшего порядка работ. Развивать выбранный «Фокус», сохраняя
светлую палитру и shadcn. Ниже уточняются и дополняются требования раздела 2,
а не создаётся второй независимый редизайн.

- Компактный список вместо крупных карточек: ориентир 36–40 px на строку,
  около 20 задач на десктопе. Галочка, статус, превью названия и номер;
  спокойное выделение выбранной строки. Поиск и фильтры сверху. При выборе
  задач появляется панель групповых действий: в очередь, в бэклог, снять выбор.
  Автообновление не меняет порядок очереди и не перемещает строки под курсором;
  активность обозначается небольшим индикатором.
- Разделить содержание и свойства задачи. Основная область: название,
  текущее состояние, результат или следующий шаг, обсуждение. Модель, ветка,
  рабочая копия, технические идентификаторы и настройки проверок — в
  сворачиваемых свойствах. Автоприёмка и положение в очереди остаются заметными.
- Верх карточки отвечает на вопрос «что происходит»: текущая работа,
  выполняемые проверки, результат для приёмки, конкретная блокировка или
  факт применения. Действия соответствуют состоянию. Длинные повторяющиеся
  пояснения кнопок доступны по запросу.
- Единая лента обсуждения содержит сообщения, вопросы, решения и итоговые
  сводки. Служебные события и вызовы инструментов — в отдельном раскрываемом
  журнале. Поле сообщения закреплено снизу; «Обсудить» и отправка замечаний
  с продолжением явно различаются. Обычное сообщение не снимает паузу.
- Короткая постоянная навигация: «Нужно решение» со счётчиком, «Задачи»
  с представлениями «Бэклог / Очередь / Все», «История». Проект выбирается
  сверху, настройки снизу. Отдельные разделы каждой роли пока не нужны.
  В блокировках видны причина, чьё действие требуется и длительность ожидания.
- Постоянная ссылка на приложение находится в верхней панели проекта.
  Рядом показаны задача, версия и готовность; предыдущая рабочая версия
  явно отличается от результата текущей задачи. Адрес не спрятан в деталях.
- Уменьшить число вложенных карточек, рамок, цветных заливок и пустых
  отступов. Цвет выделяет состояние, выбор и основное действие; статусы
  различаются также текстом и формой значка. Сохранить выравнивание сверху.

Предварительная последовательность внутри бэклога: компактный список →
ясный верх карточки и свойства → лента обсуждения и раздел решений.
Это не разрешение начать реализацию сейчас.

Проверки при реализации: плотность на согласованном десктопном размере,
читаемость длинных названий, выбор и групповые действия, сохранение порядка,
фокуса, прокрутки и черновика при SSE; доступность с клавиатуры и понятность
статусов без цвета; верность задачи/версии у ссылки на приложение.

Источники визуальных ориентиров:

## 9. Правила исполнения — согласовано 2026-11-06

- Ожидание человека блокирует зависимые задачи. Независимые продолжают работу
  в собственных ветках; это не разрешает увеличивать число одновременно
  работающих агентов. Их результаты не подменяют ожидающую приёмки версию.
- Обычные изменения кода допускают автоприёмку после обязательных проверок.
  Спорные требования, существенные изменения UX, удаление данных, миграции
  с риском потери данных и внешние действия требуют решения человека.
  Руководитель объясняет причину остановки; контроллер обеспечивает ограничения.
  Перед ночным запуском видно, у скольких выбранных задач включена автоприёмка.
- QA интерфейсной задачи запускает приложение и проверяет пользовательский
  сценарий в браузере, сохраняя доказательства. Одних тестов недостаточно.
  Невозможность открыть результат блокирует автоприёмку.
- Обсуждение уточняет контекст, сохранение в бэклог фиксирует намерение,
  постановка в очередь разрешает исполнение. Продолжение после явной паузы —
  отдельное действие; обычное сообщение не запускает работу.
- Tw и его интерфейс развиваются отдельно от выполнения других проектов:
  либо работа над Tw, либо работа над прикладными задачами. Одновременного
  исполнения этих двух режимов не допускаем. Это не отменяет сохранение
  состояния и проверку восстановления при обновлении.

Эти уточнения заменяют прежнюю формулировку об остановке всей последовательной
очереди при ручной приёмке. Реализация по-прежнему отложена; согласование правил
не является командой запуска worker или приёмкой существующих задач.

## Порядок продолжения

При возобновлении проверить лимит и актуализировать контрольную точку.
Сначала достоверность просмотра и TASK-007, затем UI/SSE и бэклог/очередь.
Раздел решений включить в UI, критерии готовности — в постановку задач,
контроль зависаний — в проверку надёжности ночной очереди.
Автоприёмка зависит от проверяемой последовательной интеграции и независимых
review/QA. Изоляция runtime и данных из прежнего плана остаётся обязательной
зависимостью соответствующих адаптеров; удобство интерфейса её не заменяет.
Уточнение Docker и планирование выбранного пилота можно обсуждать до реализации.
