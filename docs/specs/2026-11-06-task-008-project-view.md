## Контракт

`project_view` разрешает чтение и управление только при точном значении true. Без полномочия нет запросов view и operations и нет runtime controls. Команды дополнительно требуют непустой CSRF и строковой непустой revision из последнего актуального GET просмотра. Revision управления задачей не используется. Readonly с пустым CSRF не отправляет команды.

Scoped transport уже добавляет `projects/{id}/`. Используются GET и POST `tasks/{id}/view`, GET `operations/{id}`. GET возвращает `{task_id,available,reason,revision,view}`, revision — строка либо null. View содержит revision опубликованного результата, постоянный адрес, running, requested с задачей/режимом/revision, active_task, mode, source_digest, current, building, message и возможную error. POST передаёт `{action:"select"|"refresh",mode:"checked"|"working"}`, CSRF, Idempotency-Key и If-Match. Origin обеспечивает существующий same-origin транспорт.

Операция содержит operation_id, task_id, status pending/succeeded/failed, возможные view и error. Ошибка внутри успешного HTTP обрабатывается как отказ. Succeeded означает принятие запроса, а не готовность сборки. Готовность подтверждает актуальный GET с available, running, current, отсутствием building/error, совпадающими выбранной задачей, active_task и режимом. Requested должна содержать выбранную задачу и режим просмотра; view.revision должна равняться requested.revision + ":" + source_digest. Верхний revision служит только для If-Match. Противоречивые данные не доказывают готовность.

## Интерфейс

Компактный блок «Просмотр приложения» различает отсутствие, остановку, подготовку, готовность, ошибку и сохранённую предыдущую версию. Причины reason/message/error отображаются безопасным текстом. Видны активная и запрошенная задачи, режим, короткая версия и постоянный адрес; UUID и полные digest доступны в раскрываемых подробностях. Рабочая версия явно неподтверждённая. При другой активной задаче видна предыдущая версия и предупреждение о переключении.

Кнопки «Показать проверенную версию» и «Показать рабочую версию» отправляют select. «Повторить подготовку» отправляет refresh для известного запрошенного или активного режима выбранной задачи. Если режим неизвестен, нужен явный select. Выбор карточки и reload не отправляют POST. Эти действия не принимают задачу, не запускают worker и не меняют main.

«Открыть результат» использует только проверенный loopbackUrl адрес Task.preview с сохранением пути и параметров. Голый view.url показывается как адрес, но не подставляется в ссылку результата. Persistent preview требует current=true, read_only=true и совпадения режима с подтверждённым просмотром выбранной задачи. Строковая Task.preview.version должна равняться source_digest; верхний revision используется только для If-Match. Legacy preview только с URL сохраняет самостоятельную ссылку; явно отрицательные и неполные новые метаданные не обходятся через fallback. Причины отсутствия адреса, неподдерживаемого адреса и неподтверждённого соответствия различаются.

## Асинхронность и повтор

Отдельный hook изолирован по проекту, задаче и capability; компонент в карточке дополнительно получает ключ проекта/задачи. GET выполняется последовательным polling с AbortController, cleanup, флагом alive и идентификатором запроса. Поздние GET, POST и операции не меняют новый scope или размонтированный компонент. Фоновый GET сохраняет последние данные; ошибка отмечает их устаревшими и запрещает новую команду до актуального GET.

До POST sessionStorage сохраняет project/task, исходное тело, revision, ключ и при наличии operation_id. Слот `tw-web:pending:project:{project}:view:{task}` отделён от действий задачи. Структура и scope восстановленной записи проверяются. Ошибка сохранения отменяет отправку; неопределённая операция и синхронная блокировка защищают от новых команд и двойного клика.

При сетевом сбое явный повтор использует прежние тело, ключ и revision. Если operation_id известен, проверяется прежняя операция без нового POST. Reload не возобновляет команды автоматически. После pending операции GET operations выполняется последовательно; ошибка чтения оставляет явный повтор. Окончательный отказ обновляет GET view. Конфликт revision не вызывает автоматическую новую команду с исправленной revision.

## Допущения

Контракт и предоставленная выдержка react.dev о cleanup эффектов достаточны для этапа; сеть, MCP, браузер и дополнительные агенты запрещены. Нужные сведения о React уже получены до этого этапа. Операционная ошибка сохраняется в блоке до следующей явной команды, даже если фоновые GET снова успешны. Неизвестные или неполные метаданные трактуются консервативно. Зависимости и конфиги не изменяются.

## Критерии и проверка

- Сохраняются «Фокус», функции TASK-006, документация и человеческая приёмка.
- Только явное действие отправляет select/refresh с правильным режимом и revision просмотра.
- Без capability нет view/operations и runtime controls; readonly не отправляет команды.
- Другая активная задача, предыдущая версия и переключение явно обозначены.
- Состояния и конкретные причины видны без JSON; рабочая версия неподтверждённая.
- Фоновый GET сохраняет блок; устаревшие данные запрещают новую команду.

- Scoped URL, CSRF, Idempotency-Key и If-Match используют существующий transport.
- Failed/error внутри data не превращается в успех; pending проверяется через operations; succeeded не доказывает готовность.
- Повтор после сети/reload явный и точный, scope изолирован, известная операция проверяется без POST.
- Двойной клик не дублирует команду; ошибка storage отменяет POST; capability блокирует восстановленную команду.
- Ссылка сохраняет task-bound preview URL; противоречивые метаданные и неподдерживаемый адрес не открываются; legacy fallback сохранён.
- Сценарные frontend-тесты покрывают переключение, previous task, capability, readonly, поздние GET/POST, stale revision, failed envelope, retry/scope, storage, polling и готовую ссылку.

## Состояние проверки

Продолжение по замечанию о HTTP 409: окончательный HTTP-отказ удалял pending, но сохранял ожидание отклонённого режима. Теперь обрабатываемый окончательный HTTP 4xx сбрасывает ожидание и инициирует актуальный GET; сетевой сбой сохраняет прежнюю команду и ожидание. Регрессия выбирает working при готовом checked, получает 409 и проверяет ошибку, возврат к «Готово», отсутствие «Подготовка», сохранение persistent-ссылки checked с путём и параметрами и единственный POST. До актуального GET данные остаются устаревшими. Локально node_modules отсутствует; регрессия не запускалась, проверки переданы контроллеру.

Продолжение после замечаний контроллера: существующая реализация сверена с планом. Ошибка, отсутствие и остановка из GET имеют приоритет над ожиданием принятой команды. Ожидаемый режим сохраняется до подтверждённой готовности соответствующего просмотра, чтобы предыдущая версия другого режима не стала готовым результатом. При подтверждении готовности ожидание сбрасывается. Pending продолжает блокировать готовую ссылку и новые команды независимо от отображаемого состояния.

Добавлены регрессии succeeded → ошибка/остановка/отсутствие с повторными GET, полный цикл refresh → pending → operations succeeded → подтверждённый GET и поздний ответ operations после смены проекта. В текущей копии отсутствует node_modules, поэтому новые frontend-тесты локально не запускались. Результаты предыдущих запусков контроллера не подтверждают эти изменения; требуется новый запуск контроллером.

Выполнено чтение и статическая сверка разрешённых исходников. Локальные frontend-проверки недоступны в предоставленной копии; зависимости не устанавливались. Независимые проверки не запускались и не объявляются успешными. Контроллеру передаются Vitest, TypeScript, production build и заданный Python unittest. Browser QA не выполнен.

Последнее уточнение совместимости: preview вида {url, read_only:true} является legacy. Существующие изменения сверены с планом и result_feedback. Верхний data.revision используется только для If-Match. requested.revision содержит UUID выбора; опубликованный view.revision должен равняться requested.revision + ":" + source_digest. Модель и валидация включают view.revision. Готовность дополнительно требует согласованных requested.task/mode, active_task, current, running и отсутствия building/error. Неполные сведения, включая отсутствующий requested, не подтверждают готовность.

Persistent-ссылка требует строкового preview.version, равного source_digest, а также подтверждённой готовности выбранной задачи, совпадения режима, current=true и read_only=true. Используется только task-bound preview URL с сохранением пути и параметров. Legacy fallback сохранён. Основной вид показывает короткую версию; UUID и полные digest/revision находятся в закрытых подробностях.

Регрессии используют разные UUID выбора и SHA256 токен If-Match, реальную view.revision и совпадающую версию preview. Проверяются переход succeeded → подготовка → готовность, несовпадающая/отсутствующая/числовая preview.version, неверные UUID и digest опубликованной ревизии, отсутствие requested и независимость готовности от токена If-Match.

Локальные frontend-проверки недоступны: node_modules отсутствует. Зависимости не устанавливались. Frontend tests, TypeScript, build и Python unittest переданы контроллеру; независимые проверки не запускались. Browser QA и окончательная приёмка остаются человеку.
