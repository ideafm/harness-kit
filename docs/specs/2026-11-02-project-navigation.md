# Проекты и задачи в веб-панели

Задачи принадлежат проекту: у каждого проекта уже есть отдельное состояние,
очередь и worker. Панели нужен реестр подключённых проектов и явный выбор.
Номера TASK-001 могут повторяться между проектами; полный адрес содержит ID
проекта и номер задачи. Существующие задачи не переносить и не принимать.

Контроллер хранит реестр в собственном состоянии основного проекта. API
возвращает только ID и имя. Подключение существующего проекта выполняется
человеком через форму доверенного origin подтверждений, с CSRF и явным путём.
Произвольные пути через JSON API, скрытые каталоги и symlink запрещены.
Подключаются только проекты, уже инициализированные командой tw init.

Маршруты /api/v1/projects/{id}/status, tasks, operations и capabilities
работают с выбранным проектом. Подтверждения привязаны к этому же проекту,
версии и revision. Старые маршруты сохраняют основной проект и совместимость.
Неизвестный проект не подменяется основным. Список проектов содержит ссылку
на доверенную форму подключения. Никакого расширения агентского MCP.

Интерфейс: проекты в sidebar, задачи только выбранного проекта, создание задачи
в выбранном проекте; сброс выбранной задачи и pending при переключении.
Небольшая правка типографики, отступов и визуальной иерархии без новых пакетов.
При запуске tw в папке автоматически подключать её как проект; повторный запуск
не создаёт дубликатов. Если отсутствует команда проверок, запрашивать только её.
Выбранные проект и задача сохраняются в URL через непрозрачные ID, без путей
и текста задач; обновление страницы и возврат из подтверждения сохраняют контекст.

## Прогресс задачи

Уточнение пользователя: прогресс-бар относится к каждой задаче, не к проекту.
Показать последовательность «Спецификация и план → Реализация → Проверки →
Ревью → Приёмка». Это этапы процесса, не оценка процента выполненной работы.
Текущий backend объединяет исследование, спецификацию и план в одном этапе
plan; implement — реализация, check — проверки, review — независимое ревью.
stage=done означает завершение автоматического конвейера: state=review ещё
ждёт приёмки, state=accepted означает принятие человеком. Не показывать
приёмку завершённой по одному stage=done; rejected — отдельный итог отклонения.

Отдельные шаги «Исследование», «Спецификация», «План» без новых backend-сигналов
не показывать завершёнными: соответствующие документы создаются одним этапом.
Ожидание согласования плана, вопроса, лимита, пауза и блокировка показываются
у текущего шага отдельным статусом. При повторной реализации после красных
проверок или доработки прогресс отражает текущий этап, а не монотонный процент.
Неизвестные этапы имеют нейтральное отображение, без предположения о готовности.
На телефоне шаги остаются читаемыми; текущее положение доступно скринридеру.

Пользователь запросил сейчас только обновление плана. Реализацию по старой
версии плана TASK-003 не запускать; включить эти уточнения в новую версию.
Правки интерфейса должны идти через Tw согласно AGENTS.md проекта tw-web.
В текущей сессии MCP Tw отсутствует; это явная зависимость frontend-части.

## Контракт для frontend

- `GET /api/v1/projects` → envelope `data: {items: [{id, name}],
  default_project_id, connect_url}`. Полные пути в списке не возвращаются.
- `connect_url` открывается как отдельная страница. GET ничего не подключает;
  человек вводит путь и отправляет форму. Новые проекты сначала требуют `tw init`.
- Выбранный ID задаёт prefix `/api/v1/projects/{id}` вместо `/api/v1` для
  status, capabilities, tasks, tasks/{n}, tasks/{n}/control, events,
  artifacts/{name}, tasks/{n}/actions и operations/{uuid}.
- `/api/v1/session` остаётся общим: тот же CSRF и origin, прежние схемы
  payload, If-Match и Idempotency-Key. Старый prefix обслуживает основной проект.
- Использовать confirmation_urls из control без самостоятельной сборки URL.
  Подтверждение уже содержит проект; форма показывает его имя и ID.
- `?project={id}&task={n}` — ссылка возврата. До frontend-интеграции панель
  ещё не интерпретирует project; не считать эту ссылку готовым переключателем.
- После возврата из подключения обновить список проектов. При смене проекта
  сбрасывать выбранную задачу и изолировать кэши/operation IDs/pending по ID.
  Запоздалый ответ старого проекта не должен перезаписывать выбранный проект.

## Отдельная следующая задача: рабочая панель worker

Пользователь просит улучшить UI отдельной задачей: функциональность в целом
устраивает. Дополнительно «Worker работает» должен открывать текущую фоновую
работу: проект, задачу, этап, время запуска, последнее действие, проверки,
причину ожидания, историю событий и переход к результату. Не рисовать активную
работу по одному живому PID: различать простой очереди, запуск, выполнение,
проверки и ожидание. Позволять перейти к выполняемой задаче одним нажатием.

Просмотр процесса в реальном времени потребует отдельного controller API:
отдавать разрешённые события действий и вывод проверок как недоверенный текст,
не публиковать сырые внутренние логи, токены или приватные рассуждения.
Текущий events API отражает жизненный цикл этапов, не все команды агента.

Обсуждение с исполнителем проектировать как сохраняемые сообщения контроллеру
с состояниями «ожидает доставки», «доставлено», «нужен ответ». Уточнения передаются
на границе этапа или после паузы с продолжением; критическое изменение обновляет
план и его версию. Прямого подключения к stdin текущего exec пока нет.
Не обещать существующий интерактивный канал. Просмотр не расширяет права,
сообщения не подменяют человеческие утверждения и приёмку.

## TASK-004: один экран и действия вместо информационного шума

Пользователь считает текущий набор вкладок «Обзор / Спецификация и план / Diff /
Проверки / Ревью / События» перегруженным и не отвечающим на вопросы «Что мне
проверить?» и «Что делать дальше?». Основной desktop-экран должен помещаться
в один viewport без прокрутки страницы и вложенных скроллов. Показывать краткий
итог, текущую причину ожидания, конкретную проверку для человека и следующий
шаг с кнопками. Когда участие человека не требуется, сообщать это явно.
Документы, diff, проверки, ревью и историю открывать по компактным кнопкам
в доступных модалках. Длинный текст прокручивается внутри открытой модалки.
Большие списки — поиск, фильтры и пагинация. На малых экранах сохранять
читаемость и доступность действий; адаптивность не достигается скрытием данных.
Сводки не выдумывают причины и рекомендации: недостающие данные требуют API.
Требования сохранены в контексте TASK-004, реализация пока не запускалась.
