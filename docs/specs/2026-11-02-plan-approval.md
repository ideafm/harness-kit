# Режим согласования плана

Два режима задачи: `auto` и `approve-plan`. Приоритет и срочность не меняют
требований согласования. По умолчанию новые задачи — auto. Оператор может
потребовать согласование при постановке; агент не может отменить его позже.

Планировщик оценивает risk (low/high/unknown), scope (small/large/unknown)
и объясняет решение. High, unknown, large, критичные пути и явное требование
в запросе повышают режим до approve-plan. Эвристика путей — дополнительный
консервативный сигнал, не доказательство полноты классификации риска.
Старые задачи без этих полей продолжаются с прежней семантикой auto.

Контроллер сохраняет документы и сводку, затем переводит задачу в
`awaiting_approval`. Этап остаётся implement, но никакая реализация не
запускается. Утверждение привязано к SHA-256 исходного запроса, baseline,
спецификации, плана, критериев, файлов, сводки и оценки риска. Перед каждой
попыткой реализации контроллер проверяет актуальность версии и документов.
Изменённая версия требует повторного утверждения.

Оператор утверждает `tw approve-plan TASK-NNN --version SHA256 --confirm TASK-NNN`
или возвращает замечания `tw revise-plan TASK-NNN 'замечания'`. Утверждение
возвращает задачу в очередь без скрытого изменения прав. CLI показывает SHA256.
Обычные answer/resume и повторный run не обходят gate. MCP может поставить
задачу с режимом согласования, читать её статус и предложить ужесточение, но
не может утвердить/вернуть план или выдавать grants от имени пользователя.

Возврат с замечаниями сохраняет историю версий и заново запускает планирование.
Поскольку реализация ещё не разрешалась, такой возврат не смешивает новые
спецификации с частично сделанной работой: при уже начатой реализации нужен
отдельный разбор. Утверждение результата остаётся отдельным действием.

Декомпозиция сейчас — только шаги в Markdown. Дочерние задачи, зависимости,
допуск дочерних задач и интеграция результатов в общий baseline в этот проход
не входят. Для большой задачи планировщик предлагает разбиение в плане,
а контроллер требует согласования.

Работающий worker не перезапускается и не получает новые модули посреди задачи.
Новые правила будут действовать в новых процессах контроллера. Изменений
legacy Claude, sandbox-политик и коммитов в этом проходе нет.
