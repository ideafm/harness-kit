# Входящая большая задача и проверенная интеграция

## Цель

Входящий запрос превращается в ограниченный набор связанных задач с общими
критериями. Существующий worker исполняет очередь; управляющий агент пользуется
контроллерными операциями. Самостоятельное пополнение бэклога не требуется.

## Первый этап: объединённый результат

Перед изменением основной ветки контроллер строит Git merge-tree из текущего
HEAD и принятого результата. Конфликт останавливает только эту интеграцию.
В безопасный временный snapshot экспортируются обычные разрешённые файлы.
Команда проверок проекта выполняется через проверенную внешнюю песочницу;
для подготовленного frontend используется существующий toolchain.

Receipt связывает исходный HEAD, результат задачи, дерево кандидата, команду,
scope, backend, digest исходников и журнал. Изменение snapshot во время проверок
запрещает интеграцию. Перед применением повторно проверяются HEAD, ветка и
чистота основной копии. Применяется именно проверенное дерево; повтор не
создаёт дополнительных коммитов. Ошибка оставляет основную копию и публикацию
прежними, зависимые задачи продолжают ждать. Нет unrestricted fallback.

Существующие успешные интеграции не переигрываются. Незавершённая интеграция
без нового receipt повторно проверяется. Проверка объединённого кода не заменяет
независимое ревью критериев и существующие правила человеческой приёмки.

## Следующий этап: минимальный оркестратор

Сохранять исходный запрос, общие критерии, подзадачи и зависимости как одну
операцию. Повтор постановки не создаёт дубликаты. Все подзадачи используют
действующие gates, ограничения и scheduler. Общий результат не объявляется
готовым только по числу завершённых подзадач: нужна итоговая проверка критериев.
Сначала один исполнитель. Бюджеты, изменение плана и управляемое исправление
курса развиваются поверх этой модели, без конкурирующего scheduler.

## Реализуемый контракт большой задачи

CLI goal-submit и MCP tw_submit_goal принимают request, criteria (1–50), tasks
(1–20), request_key, start, необязательные approval/placement. Подзадача содержит
key, request и depends_on — уникальные ключи ранее перечисленных подзадач.
Вся постановка выполняется в одной транзакции SQLite. Одинаковый ключ с другим
содержимым отвергается. Исходное требование согласования наследуется подзадачами.

Контроллер добавляет verification_only задачу с зависимостью от всех подзадач.
Она не вызывает implement, не может планировать изменения и получает неизменённые
исходные criteria. Ошибка checks/review останавливает её с причиной. Pass остаётся
на человеческой приёмке независимо от политики автоприменения.

tw_goals/tw_show_goal и CLI goals/goal-show показывают состояние большой задачи:
in_progress, needs_attention, awaiting_acceptance, completed или stale_verification.
Последнее означает, что дерево main изменилось после проверки; приёмка старой
итоговой проверки блокируется. Итог относится к committed main, не к локальным правкам.

tw_recheck_goal/goal-recheck создаёт новую итоговую проверку после blocked или
stale_verification. Дополнительные depends_on — существующие задачи исправления.
Ключ повторной операции идемпотентен; прежние проверки и их документы сохраняются.
Активную проверку, отклонённую цель или обычное ожидание этим действием не обходят.
Автоматического пересмотра состава подзадач и бюджетирования пока нет.

## Проверки первого этапа

Успешное слияние и повтор; семантически несовместимые изменения без Git-конфликта;
конфликт; изменение HEAD/рабочей копии во время checks; отказ песочницы; изменение
исходников проверкой; восстановление после прерывания; ожидание зависимых.
