# tw-web: один вход и управление циклом из браузера

**Режим:** approve-plan. Операции меняют состояния задач, утверждают планы и
принимают результаты; перед реализацией требуется решение пользователя.
**Статус:** план подготовлен; короткая команда реализована, действия UI ещё нет.

## Вход

`tw-web` из любой папки запускает один локальный сервис и открывает браузер.
Порт 47831, project, controller и выбранная версия панели определяются при
подключении. Shell-конфиги не меняются. Установлена символическая ссылка
`/opt/homebrew/bin/tw-web` на launcher проекта; существующие команды не заменяются.
Выбор просмотренного результата сохраняется в принадлежащем launcher состоянии.
При повторном запуске после остановки открывается тот же проверенный результат.

## Веб-цикл

Главный экран: новая задача, очередь, блок «Требует решения». Карточка содержит
этап, состояние, текущий вопрос, спецификацию, план, сводку, diff, проверки,
ревью и события. Доступные кнопки определяются состоянием контроллера:

- queued/rate_limited: запуск; queued/running/rate_limited: пауза.
- paused/blocked/rate_limited: продолжить; waiting: ответить.
- awaiting_approval: прочитать спецификацию и план, утвердить их точную версию
  либо вернуть замечания. Обычный ответ не утверждает план.
- review/done: посмотреть результат и принять его отдельным явным действием.
- accepted: отдельно применить к исходнику после проверок применимости.

Браузер не просит вводить порт, путь к workspace или команды терминала.
Предпросмотр запускается из карточки задачи. У непроверенного результата нет
возможности утвердить себя или обращаться к операторским действиям через
собственный JavaScript. Для этого preview получает отдельный origin/изолированный
контекст, а операторские подтверждения обслуживает доверенный контроллер.

Приёмка и применение — две отдельные операции. UI явно показывает, что
принятый результат ещё не перенесён в исходник. Применение не создаёт коммит,
не перезапускает worker и не обновляет запущенный код контроллера автоматически.
Если безопасного применения нет, кнопку блокируют с объяснением.

## Контроллер

Операции остаются в harness-kit и используют общие проверки переходов.
Нужен отдельный операторский канал: агентский MCP по-прежнему не умеет
approve-plan, accept, apply или grants. Проверки точной версии, подтверждения,
состояния, CAS и неизменности проверенного дерева выполняет контроллер.
Ровно одна операция при повторной отправке: request ID и сохранённый результат.
Подтверждения не должны повторяться автоматически после неизвестного исхода.

HTTP только loopback. Изменения требуют same-origin, JSON, CSRF-защиту и явное
подтверждение пользователя для плана/приёмки/применения. Произвольных путей,
shell-команд, SQLite-доступа и расширения разрешений у браузера нет.

## Разработка и границы

Контроллер меняется отдельной задачей в harness-kit. UI разрабатывается через
harness в tw-web. Существующая TASK-001 не считается принятой за пользователя;
её проверенный результат можно использовать как вход следующей итерации
в новой изолированной копии без принятия и применения исходного результата.
Для этого потребуется проверяемое продолжение от результата либо разрешённая
интеграция baseline; временные ручные коммиты не создаются автоматически.

В первый рабочий проход входят постановка, план, вопросы, пауза, просмотр и
приёмка. Безопасное применение и откат — отдельная задача контроллера;
доступность этой операции нельзя имитировать кнопкой. Не входят публикация,
LAN-доступ, browser QA без разрешения, grants и автокоммиты.

Проверки: общие переходы и операторский протокол в unittest контроллера;
маршруты и CSRF/Origin/Host, повторные запросы и подтверждения в тестах UI;
реальный local HTTP smoke без изменения сетевого профиля worker.
