# Спецификация: Обратимое удаление задачи и вкладка «Удалённые»

Дата: 2026-11-08. Статус: на рассмотрении / архитектурная сверка.

---

## 1. Цель и требования к поведению

1. **Обратимое удаление задачи:**
   - В карточке задачи доступно действие «Удалить» с подтверждением через диалоговое окно (без ввода текста или сложных проверок).
   - После подтверждения задача исчезает из основного списка задач и появляется во вкладке «Удалённые».
   - Задача в состоянии `running` (выполняющаяся) не может быть удалена: действие «Удалить» отключено с явным пояснением: *«Работающую задачу удалить нельзя»*.

2. **Вкладка «Удалённые» и восстановление:**
   - Над списком задач размещаются вкладки: основной список задач («Активные» / «Все») и вкладка «Удалённые».
   - Во вкладке «Удалённые» отображаются ранее удалённые задачи.
   - Для удалённой задачи доступно действие «Восстановить».
   - При восстановлении задача возвращается в основной список с полным сохранением всех исходных данных, этапов, истории событий и артефактов (`specification`, `plan`, `diff`, `review` и т.д.).

3. **Автономное выполнение и безопасность очереди:**
   - Удалённая задача немедленно исключается из очереди планировщика воркера и никогда не запускается автоматически.
   - Восстановление задачи возвращает её в неактивное состояние (`paused` или исходное сохранённое) и **НЕ запускает выполнение автоматически**.
   - На данном этапе исключены: массовые действия над задачами (batch operations) и окончательное безвозвратное удаление (hard delete / purge).

4. **Запрет клиентской имитации:**
   - Удаление должно быть честным серверным состоянием контроллера, а не локальным скрытием в памяти браузера (`localStorage` / React state).
   - Прямое редактирование файла базы данных SQLite (`state.sqlite`) из веб-приложения категорически запрещено.

## 2. Контроллерный контракт (`harness/`)

Для обеспечения серверного состояния требуются следующие изменения в ядре контроллера:

1. **Модель состояний в `harness/state.py`:**
   - Добавление состояния `trashed` в множество допустимых состояний `STATES` (либо фиксация обратимого удаления через поле `task['data']['deleted'] = True` с сохранением предыдущего состояния `task['data']['previous_state']`).
   - Метод `Store.runnable()`: фильтрует задачи, исключая задачи в состоянии `trashed` (или с флагом `deleted: True`).
   - Методы `Store.delete(task_id)` и `Store.restore(task_id)`:
     - `delete(task_id)`: проверяет, что `task['state'] != 'running'`. Переводит задачу в `trashed`, сохраняет событие `task_deleted`.
     - `restore(task_id)`: переводит задачу обратно в `paused` (или `previous_state`), сохраняет событие `task_restored`. Автоматический запуск воркера запрещён.

2. **Сервисный уровень в `harness/service.py` и `harness/operator.py`:**
   - Добавление действий `delete` и `restore` в `ACTIONS`.
   - В `Operator.control(ident)`:
     - Если `task['state'] == 'running'`, действие `delete` не включается в `allowed_actions`, либо передаётся в метаданных как заблокированное с причиной.
     - Для всех неработающих активных задач `delete` добавляется в `allowed_actions`.
     - Для удалённых задач доступно исключительно действие `restore`.
   - В `Operator.capabilities()`: объявление поддержки `delete: True`, `restore: True`.

3. **HTTP API в `harness/web.py`:**
   - В `GET /api/v1/status`: поддержка параметра фильтрации или атрибута `deleted: bool` в объектах задач, позволяющего клиенту разделить активные и удалённые задачи.
   - В `POST /api/v1/tasks/{id}/actions`: обработка `{action: 'delete'}` и `{action: 'restore'}` с проверкой CSRF, `Idempotency-Key` и `If-Match` ревизии.

## 3. Контракт веб-интерфейса (`web/`)

1. **Компоненты навигации и списков:**
   - В заголовке над списком задач добавляется селектор вкладок (Tabs): «Задачи» / «Удалённые» с отображением счётчиков.
   - При выборе вкладки «Удалённые» отображается список корзины.
2. **Карточка задачи и действия:**
   - В блоке действий задачи (`task-actions.tsx`) добавляется кнопка «Удалить».
   - Если задача `running`, кнопка неактивна (disabled) с подсказкой/пояснением *«Работающую задачу удалить нельзя»*.
   - Нажатие «Удалить» открывает диалог подтверждения: «Удалить задачу TASK-xxx? Задача будет перемещена во вкладку 'Удалённые'».
   - Подтверждение отправляет стандартное действие через транспорт контроллера (`actions: {action: 'delete'}`).
   - В карточке удалённой задачи отображается кнопка «Восстановить», отправляющая `{action: 'restore'}`.

## 4. Архитектурная сверка границ рабочей копии Tw

1. **Границы проекта `web`:**
   - Рабочая копия Tw-проекта `web` (`web/.harness`) ограничена исключительно директорией `web/**`.
   - Согласно правилу `web/AGENTS.md` (строка 19):
     > *«Do not change the sibling harness-kit as part of a tw-web task. Record required engine changes as separate tasks and apply them independently. Reuse core task operations in the controller; do not implement parallel state transitions or write its SQLite tables directly from the web app.»*
   - Изолированная среда выполнения (Seatbelt sandbox) запрещает агенту выход за пределы `web/`.
   - Поэтому задача в проекте `web` **физически не может изменить файлы контроллера** `harness/state.py`, `harness/service.py`, `harness/operator.py` и `harness/web.py`.

2. **Границы корня `harness-kit`:**
   - Корневая папка `harness-kit` в текущий момент не является инициализированным Tw-проектом (`tw status` возвращает требование выполнить `init`).

3. **Состояние квот:**
   - **Codex:** недельный лимит израсходован на **96%** (превышает порог Guard 95.0%). Любая попытка запустить задачу на Codex немедленно приведёт к `QuotaPause`.
   - **Gemini:** 5-часовое окно — **4.84%**, недельное окно — **15.52%**. Лимиты Gemini полностью свободны и пригодны для выполнения задач.

4. **Состояние очереди и `TASK-009`:**
   - В проекте `web` задача `TASK-009` находится в состоянии `waiting` (ждёт решения человека по файлам SSE). По правилам проекта мы не отвечаем на вопрос и не меняем статус `TASK-009`.
