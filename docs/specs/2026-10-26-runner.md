# Исполнитель бэклога: набор → исполнение → приёмка

**Цель:** набрать задачи из `docs/backlog/`, запустить и уйти (на час или на ночь), а потом принять результат по карточкам. Решения человек принимает до запуска и при приёмке, исполнение идёт без него и не мешает ему работать в своей папке.

**Результат:**

- `scripts/run.sh` — исполнитель: цикл по очереди задач в отдельном git worktree, на каждую свежий `claude -p` со своим контекстом.
- `/tw:run` — команда набора: бэклог с чекбоксами, подготовка входящих задач, коммит спеки и плана в ветку задачи, запуск исполнителя.
- `/tw:accept` — приёмка задач из бэклога вариантами; действия приёмки — командами `scripts/accept.sh`.
- Панель хода исполнителя — модуль плагина tw, открывается сама при старте прогона.

**Готово, когда:**

- `/tw:run` показывает задачи бэклога вариантами с множественным выбором (P0–P1 и свежие первыми, до 16); выбранные `готова` встают в очередь `.claude/tw-state/queue`, выбранные `входящая` по одной проходят `tw:spec` → `tw:plan` с человеком и после «да» становятся `готова`.
- Спека и план после «да» коммитятся в ветку задачи `tw/B-NNN` (создаётся от базы), без переключения ветки и без коммита в базу; рабочее дерево пользователя после этого не меняется, кроме файла задачи в бэклоге.
- `/tw:run` спрашивает режим (вся очередь / до N задач) и запускает `scripts/run.sh` в фоне, печатает, где смотреть ход. Второй исполнитель на тот же проект не стартует.
- Исполнитель работает в отдельном worktree `.claude/worktrees/tw-run`, основную папку пользователя не трогает (кроме файлов бэклога и `tw-state`); задачи строго по одной. В worktree копируется `.claude/tw.json`, ставятся зависимости проекта, Docker-окружение общее с основной папкой (`COMPOSE_PROJECT_NAME` по имени проекта).
- Каждая задача: переход worktree на ветку `tw/B-NNN`, статус `в работе`, свежий `claude -p` с её планом и текстом задачи; Stop-конвейер (check → scope → проверяющий) работает как в обычной сессии, проверяющий видит всю работу ветки против базы; после зелёного и «да» проверяющего — коммит в ветку, статус `на приёмке`, ветка освобождается.
- Задача застряла (Stop отдал человеку, проверяющий «нет» после доработки, сбой окружения, нет ветки с планом) — незакоммиченное сохраняется коммитом `wip` в ту же ветку, статус `застряла: <причина>`, исполнитель берёт следующую. Два сбоя окружения подряд — останавливает весь прогон.
- Лимиты: исполнитель читает `rate_limit_event` из `stream-json`; при `five_hour` ≥ 95 % новую задачу не берёт и ждёт до `resetsAt` + 60 с. Ошибка лимита посреди задачи — та же пауза и повтор задачи.
- Прогон останавливается командой `run.sh stop`: дерево процессов задачи гасится, незакоммиченное — `wip`-коммитом, задача снова `готова` и первая в очереди.
- Каждая смена статуса — строка в журнале задачи; итог прогона — `.claude/tw-state/run.log` и строка в `/tw:status` (сделано / застряло / ждёт приёмки).
- `/tw:accept` без аргумента показывает задачи `на приёмке` списком; по выбранной — карточка (вердикты, «на тебе», diff ветки против базы, журнал) и варианты: принять и слить в базу / доработать (задача в план ветки, статус `готова`) / посмотреть UI (команда запуска из worktree, вопрос повторяется) / отклонить (статус `отклонена: <почему>`, ветка остаётся). Действия выполняет `accept.sh`, а не агент руками.
- Панель: при старте прогона в сессии с tw открывается панель с текущей задачей, действиями агента, строками `tw ▸` и хвостом `run.log`; `/tw-watch` открывает и закрывает её вручную. В `claude -p` панель не включается.
- Прогон проверен на `~/tutor-saas` на двух реальных задачах S из бэклога.

**Не трогаем:** `hooks/guard.sh`.

**Не цель:** параллельные задачи (шаг 10); денежный лимит на задачу; запуск по расписанию (cron); слияние в базу без человека; деплой.

**Входные данные:** формат `docs/backlog/B-NNN.md` (`tw:task`), Stop-конвейер, `rate_limit_event` в `stream-json` (проверено: `five_hour.utilization`, `resetsAt`), карточка `scripts/accept.sh`, API модулей плагина (`ui.render` Pane, `session.start` с `isInteractive`).

**Допущения:**

- Коммит в свою ветку `tw/B-NNN` без «да» человека разрешён; в базу — только через `/tw:accept`.
- Ветки от базы (`runBase`, по умолчанию `main`); конфликт при слиянии — `accept.sh rebase` во временном worktree, конфликт при rebase — человеку `[допущение]`.
- Слияние идёт в папке пользователя: она должна стоять на базе и быть чистой (кроме бэклога) `[допущение]`.
- Бэклог живёт в папке пользователя (как есть: в git или нет); агент исполнителя получает текст задачи в промпте, статусы пишет только исполнитель `[допущение]`.
- База данных и контейнеры общие у пользователя и исполнителя `[допущение]`: два набора контейнеров на одних портах не поднять.
- Зависимости в worktree — `<pm> install --frozen-lockfile` (или `runInstall` из `tw.json`) перед задачей, если lock-файл изменился `[допущение]`.
- Денежного лимита нет: держат лимиты подписки и круги Stop.
- `claude -p` исполнителя запускается с `--permission-mode acceptEdits` и разрешёнными командами проекта из `tw.json` (`runAllow`), без `bypassPermissions` — `[допущение]`.
- Чекбоксы — `AskUserQuestion` с `multiSelect`; задачи сверх 16 добираются словами — `[допущение]`.
