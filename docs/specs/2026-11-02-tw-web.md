# tw-web: концепция первой версии

**Статус:** продуктовая концепция; запускаемый каркас подготовлен.

Текущий проход: [bootstrap](2026-11-02-bootstrap.md). Панель развивается
через собственный harness; Git baseline пока ожидает явного разрешения.

**Цель:** управлять задачами harness из одной панели и развивать саму панель
через тот же конвейер разработки. Пользователь видит, что идёт, что ждёт его,
почему задача остановилась, и на основании чего результат готов к приёмке.

**Разделение проектов:**

- `../harness-kit` — контроллер и общие операции задач: очередь, блокировки,
  sandbox, запуск Codex, проверки, ревью, события, восстановление.
- `tw-web` — локальный HTTP API и интерфейс, вызывающие эти операции.
- Данные задач принадлежат контроллеру. Панель не создаёт собственную копию
  состояний и не редактирует таблицы SQLite в обход общих операций.

## Главный экран

Слева список подключённых проектов; в первой версии — tw-web. Основная
часть начинается с блока «Требует моего решения»: вопросы, запросы разрешений,
ошибки и результаты на приёмке. Далее список задач с фильтрами.

В строке задачи: номер, название, проект, этап, состояние, время на этапе,
причина ожидания и следующая попытка при лимите. Этап и состояние различаются:
например, «ревью / ожидает ответа» или «реализация / пауза из-за лимита».

Новая задача задаётся обычным текстом. Панель показывает сохранённую сводку
спецификации и плана, когда они готовы, без требования нажать «продолжить».
Шкала этапов отображает подтверждённые переходы, а не придуманный процент.

## Карточка задачи

Разделы: обзор и текущий вопрос; спецификация и план; хронология; лог исполнения;
изменения; проверки и независимое ревью; приёмка. Источники данных — артефакты
и события контроллера. Контроллер отдельно сообщает о живом worker и процессе
агента, чтобы не путать сохранённое состояние running с реальным исполнением.

Действия: поставить в очередь, запустить, приостановить, продолжить, ответить
на вопрос, принять результат. Применение к исходному проекту — отдельное действие
после приёмки и проверок. Откат не удаляет историю и не запускает git reset
на рабочем проекте автоматически.

## Как панель развивается через harness

1. В начале создаём запускаемый каркас и команду проверок.
2. Подключаем проект после разрешённого исходного коммита: текущий harness
   берёт snapshot из HEAD и не видит незакоммиченный код.
3. Задачи интерфейса проходят планирование, реализацию, check и ревью в копии.
4. Пользователь изучает результат и принимает его; интеграция выполняется
   отдельно и сохраняет возможность возврата к предыдущей версии.
5. Рабочая панель обновляется только после интеграции. Закрытие вкладки или
   перезапуск dev-сервера не останавливает worker и не теряет вопросы.
6. Изменения контроллера оформляются отдельными задачами для harness-kit.
   Запущенная задача использует зафиксированную версию контроллера; обновление
   ядра проверяется отдельно и не подменяет процесс посреди работы.

## Безопасность

Все существующие гварды сохраняются. У браузера нет endpoint для произвольного
чтения файлов, исполнения команд или отключения sandbox. Разрешённые проекты
и действия определяются контроллером; project_id не является произвольным путём.
Ответ на вопрос не открывает секреты и сеть. Будущий grant требует отдельного
подтверждения конкретного действия, ресурса и срока; обычный Enter в поле
ответа не считается разрешением.

Первый HTTP-сервер слушает только loopback. Изменяющие запросы требуют защиты
от CSRF и проверки Origin/Host; локальное размещение не отменяет эту защиту.
Логи, запросы пользователя и diff выводятся как текст. Приложение не публикуется
и не получает внешние интеграции по умолчанию.

## Границы первой версии

Включаем один проект, список и карточку задач, создание задачи, события,
вопросы/ответы, паузу/продолжение и приёмку. Сначала читающая панель, затем
действия через общий API контроллера. Обновления — polling; streaming добавим,
когда появится необходимость. Backend на Python; frontend HTML/CSS/JS без npm.

Не включаем удалённый доступ, мобильные уведомления, несколько пользователей,
параллельных исполнителей, точный прогноз лимитов, автономную выдачу разрешений
и автоматическое слияние. Возможности текущего CLI не выдаём за уже готовый API.

## Что нужно до реальной разработки панели

- Общий TaskService и stdio MCP уже реализованы в harness-kit. Первая задача
  использует читающие инструменты MCP. События и приёмка пока не представлены
  этим API; расширение контроллера выполняется отдельно.
- Unit-тесты маршрутизации и транспорта выполняются без сокетов внутри
  текущего sandbox. Реальный HTTP smoke запускает внешний контроллер;
  network-профиль worker не ослабляется.
- Разрешение на browser QA перед первым использованием браузерных инструментов.
- Общая операция применения/возврата результата: сейчас применение поддерживает
  только учебный taskboard. Его helper нельзя направить на tw-web.
- Исходный Git-коммит этого проекта после отдельного разрешения пользователя.

**Допущения:** локальная панель для одного пользователя на этом Mac; русский
интерфейс; функциональность и наблюдаемость важнее оформления первой версии.

**Открытые решения:** доступ только с этого Mac или также с телефона; достаточно
ли для начала таблицы задач с боковой карточкой; насколько рано нужен браузерный
интеграционный тест и применение результатов из панели.
