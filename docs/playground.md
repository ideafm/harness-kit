# Учебная площадка

Команды ниже запускаются из корня harness-kit. Шаблон хранится в
`examples/taskboard/`, отдельный рабочий проект — в `lab/taskboard/`.
`lab/` исключён из основного Git: эксперименты не попадут в коммит harness.

Приложение — небольшой CLI-список задач: добавить задачу, отметить выполненной,
вывести список. Python и стандартная библиотека, без сервера, сети и установки
зависимостей. Семь базовых тестов проверяют поведение и JSON-вывод CLI.
Тестовые данные — отдельные файлы в рабочей папке. Текущий строгий профиль
Codex на macOS ограничивает удаление каталогов; файловые fixture позволяют
проверять приложение без ослабления гвардов. Это ограничение runtime остаётся
отдельной задачей для дальнейшей работы с более сложными проектами.

## Подготовка

```sh
python3 bin/playground prepare
```

Копирует шаблон, не создаёт коммит. Если экземпляр уже существует, команда
ничего не перезаписывает. Для следующего шага нужно явное разрешение на
начальный коммит **только учебного репозитория**:

```sh
python3 bin/playground create --confirm-initial-commit
python3 bin/playground check
```

`create` создаёт отдельный Git-репозиторий с исходным коммитом и подключает
harness. Никакие настройки Git пользователя не меняются; у начального коммита
синтетическая подпись Harness Playground. `check` сначала проверяет гварды,
затем запускает тесты приложения в sandbox.

## Первый опыт: самостоятельная задача

Для работы через привычную сессию Codex можно подключить Tw и описывать задачи
обычным языком. Уже подключённый экземпляр сохраняет очередь при повторном init:

```sh
export PATH="/Users/twist/tmp/ai/harness-kit/bin:$PATH"
cd lab/taskboard
tw init
tw
```

Выход из чата не останавливает фоновый worker; `tw stop` запрашивает его
остановку. Команды ниже — альтернативный запуск напрямую из корня harness-kit.

```sh
python3 bin/playground queue filter
python3 bin/harness --project lab/taskboard run TASK-001
```

Задача: добавить `list --status all|open|done`, сохранить старое поведение,
проверить фильтры тестами и обновить README. Полный текст —
[examples/scenarios/filter.md](../examples/scenarios/filter.md).

После подготовки плана harness выведет краткую сводку и продолжит сам.
Следить из другого терминала можно так:

```sh
python3 bin/harness --project lab/taskboard status
python3 bin/harness --project lab/taskboard show TASK-001
```

Артефакты лежат в `lab/taskboard/.harness/tasks/TASK-001/`: `specification.md`,
`plan.md`, `summary.txt`, `changes.patch`, `review.md`, `check.log`, а также
журнал запросов и ответов Codex. Это собственное состояние harness.

Ожидаемый итог — `review · done`. Изменённая версия находится в
`lab/taskboard/.harness/tasks/TASK-001/workspace/`; исходный `lab/taskboard/app.py`
всё ещё прежний. Посмотри diff и доказательства ревьюера перед приёмкой.

## Принять и применить

Эти действия выполняет человек после проверки результата:

```sh
python3 bin/harness --project lab/taskboard accept TASK-001 --confirm TASK-001
python3 bin/playground apply 1 --confirm TASK-001
python3 bin/playground check
```

Первая команда записывает приёмку. Вторая применяет diff к учебному проекту,
не создавая коммит. Применение запрещено, если исходник изменён, результат
менялся после приёмки или patch затрагивает файлы вне учебного сценария.
Сейчас это `app.py`, `tests/test_app.py`, `README.md`.
Файлы подключения Tw могут оставаться незакоммиченными: helper исключает их
из проверки чистоты только после сверки точных путей и SHA-256 с manifest init.
Любая последующая ручная правка этих файлов блокирует применение до проверки.

Новая функция в исходном проекте после применения доступна так:

```sh
cd lab/taskboard
python3 app.py add 'Купить молоко'
python3 app.py add 'Написать тесты'
python3 app.py done 1
python3 app.py list --status open
python3 app.py list --status done
```

## Откатить опыт

Сначала останови worker и активные задачи. Затем из корня harness-kit:

```sh
python3 bin/playground reset --confirm TASKBOARD
```

Команда переносит весь предыдущий экземпляр, включая данные, Git и логи,
в `lab/archive/<время>-<идентификатор>/taskboard/` и создаёт чистый проект
с новым начальным коммитом. Ничего не удаляется. Явный флаг подтверждает
архивирование и создание исходного коммита нового учебного экземпляра.
Первое задание после сброса опять получит номер TASK-001.

Сброс проверяет блокировки worker и исполнителя, а также живые subprocess.
Даже простаивающий worker нужно сначала остановить. Дополнительно старое
соединение контроллера обнаружит замену базы и откажется продолжать работу.
Архивные задачи можно читать как артефакты; продолжать их из перенесённой
папки не следует, поскольку сохранённые пути относятся к прежнему экземпляру.

## Второй опыт: вопрос человеку

```sh
python3 bin/playground queue clarify
python3 bin/harness --project lab/taskboard run TASK-002
```

Номер зависит от очереди: смотри вывод `queue`. Этот сценарий намеренно просит
неопределённую корпоративную интеграцию. Ожидаемый результат — `waiting · plan`
с вопросом, а не выдуманный API и попытка доступа к сети.

```sh
python3 bin/harness --project lab/taskboard answer TASK-002 'Интеграцию откладываем. Реализуй вместо неё экспорт списка в CSV; дальше уточним требования.'
```

Ответ сохраняется, но не открывает сеть или секреты. Запуск продолжения —
`run TASK-002` либо `worker`. Этот пример ответа меняет цель и может привести
к следующему содержательному вопросу; можно вместо него дать точный формат CSV.

## Пауза и лимиты

Во время длинного задания из другого терминала:

```sh
python3 bin/harness --project lab/taskboard pause TASK-001
python3 bin/harness --project lab/taskboard resume TASK-001
python3 bin/harness --project lab/taskboard run TASK-001
```

Для очереди с автоматическим ожиданием лимитов:

```sh
python3 bin/harness --project lab/taskboard worker
```

Настоящий лимит специально не расходуем: задержки, повторы и восстановление
проверяются сценарными тестами `tests/codex/`. Закрытые файлы и сеть проверяет
`doctor` на безопасных временных canary-файлах, без настоящих секретов.

Первый опыт расходует лимит Codex на планирование, реализацию, ревью и при
необходимости исправления. Подготовка, сброс и обычные unittest модель не вызывают.
