# Текущий контекст Harness Kit — 2026-11-12

## Продуктовая цель

Автономная система разработки с веб-панелью и несколькими подключёнными проектами.
Входящие задачи приходят от пользователя или внешнего источника: от маленького
изменения до большой цели. Управляющий агент декомпозирует запрос, отслеживает
блокировки, помогает пересматривать план и доводит работу до проверенного результата.
Поиск новых проблем — отдельная опциональная команда, не обязательный генератор бэклога.

Пользователь видит состояние, отвечает на существенные вопросы, принимает результат
или возвращает на доработку. Рутинное подтверждение каждого этапа не требуется.
Бюджеты, ограничения доступа, независимое ревью и восстановление обязательны.

## Реализованная основа

- Изолированные plan/implement/check/review, документы, SQLite, события, квоты и паузы.
- Проекты, очередь/бэклог, приёмка и доработка через доверенные формы панели.
- Preview, применение принятого результата, проверенная публикация объединённого frontend.
- Codex/Gemini и выбор backend по этапам, корзина и групповые операции.
- Зависимости ждут принятого и успешно интегрированного результата; независимая очередь продолжается.
- Автоприменение новых low/small задач только по явной проектной политике и успешному ревью.
  Код контроллера, инструкции и зависимости остаются для человека. В реальном проекте
  пользователь включил автоприменение; не менять этот выбор.

## npm dev и удаление проектов — 2026-11-11

В исходниках добавлен профиль npm-dev: tw init определяет scripts.dev,
tw configure --run 'npm run dev' включает его явно. Подготовка из существующих
node_modules и package-lock.json происходит при первом запуске, без установки
пакетов и чтения пользовательских npmrc/env. Требуется macOS и Node из Homebrew.
Внешний sandbox проверяет файлы, дочерние процессы и сеть; локальный proxy
передаёт HTTP и WebSocket. Проверенная версия использует отдельный snapshot.
Сохранённые зависимости привязаны к lockfile; обновление подготовленного runtime
после изменения зависимостей пока требует отдельного дальнейшего улучшения.

Добавлено отключение проекта через «Управление проектами» в sidebar и tw disconnect.
Файлы/история сохраняются, просмотр останавливается, работающий worker блокирует
отключение. Поддержан пустой реестр и защита от старого удаления после reconnect.
Реальные два проекта не отключались, работающая панель не обновлялась.

Проверено: 325 core, 169 frontend, 20 web Python, TypeScript и production build.
Live npm smoke без model calls подтвердил sandbox, запуск, GET/POST proxy и stop.
Настоящие Next/Nuxt/Vite проекты и WebSocket ещё требуют отдельного live smoke.
Спецификация: specs/2026-11-11-npm-dev-project-removal.md.

## Автоматические профили исполнения — 2026-11-12

Приоритет пользователя — качество. Новые проекты через tw init получают
execution_profile=auto-balanced. Для совместимости существующие проекты без поля
сохраняют manual, существующие задачи не мигрируют. Явный --model при init сохраняет
ручную семантику. Профиль новых задач проекта меняется:
tw configure --execution-profile auto-balanced|thorough|manual.
В форме создания задачи можно выбрать профиль проекта либо переопределение;
отдельный backend означает исполнителя реализации в автоматическом режиме.
CLI add и MCP/API submit также принимают execution_profile.

Auto-balanced: Sol планирует обычную задачу, Sol/Gemini реализует, Sol независимо
ревьюит. При риске/неопределённости/сложности или критических файлах Astra повторно
планирует до реализации, затем ревьюит; повышенный риск не снимает необходимость
человеческого утверждения. Thorough: Astra план/ревью, Sol/Gemini реализация.
Luna по умолчанию не используется. После двух неудачных попыток исполнитель
повышается (Gemini → Sol → Astra), только в пределах прежнего max_attempts;
лимит не увеличивается и качество не снижается при нехватке квоты. При стандартном
лимите 3 последняя попытка после Gemini выполняется Sol, затем блокировка при дефекте.

Снимок политики, пары backend/model, цели повышения и история фиксируются в задаче.
Названия GPT не передаются Gemini; модель Gemini задаётся через
--gemini-model в tw configure, иначе используется модель самого агента (явно в UI).
Ручные stage/model overrides нельзя неявно смешивать с автоматической политикой.
Старый switch_backend для автоматических задач не предлагается, чтобы не обходить
сохранённый маршрут. В карточке показаны этапы/модели и причины повышения.

Проверено 348 core, 184 frontend, 20 web Python, TypeScript и production build.
После уточнений диагностики init и теста пустой модели Gemini повторены 8 routing
тестов. Browser QA на отдельном fixture: project default balanced, выбор thorough,
Gemini implementation, сохранение backlog и показ Astra → Gemini → Astra.
Реальные модели в этих тестах не вызывались; качество и экономия пока не измерены.
