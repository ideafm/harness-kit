# Как работать с tw

tw — рельсы для работы с агентом: задача проходит спеку, план, исполнение, автоматические проверки и приёмку человеком. Решения принимает человек — до работы (спека, план) и после (приёмка). Между ними агент работает сам, а hooks не дают ему объявить «готово» раньше времени.

## Подключение проекта

1. Плагин tw подключён в `~/.claude/settings.json` (папка `harness-kit`).
2. В проекте: `/tw:init` — создаёт `.claude/tw.json` (команда проверок `check`), доказывает, что проверки умеют падать.
3. Если проекту нужны база или Docker — в `tw.json` поля `setup` и `teardown` (у tutor-saas: `pnpm infra:up` / `pnpm infra:down`). Docker Desktop должен быть запущен: setup поднимает контейнеры, но не сам Docker.
4. Проект на pnpm или yarn — в `tw.json` поле `verifyTools` с командами для проверяющего, иначе он может только `npm`/`npx`.
5. Исполнителю бэклога (необязательно, есть значения по умолчанию): `runBase` (база веток, `main`), `runModel`, `runAllow` (разрешённые команды, по умолчанию пакетный менеджер и чтение git), `runInstall` (установка зависимостей в worktree, по умолчанию `pnpm install --frozen-lockfile --prefer-offline` и аналоги), `runWorktree` (`.claude/worktrees/tw-run`), `runLimit` (порог паузы, 95), `runCopy` (неотслеживаемые файлы, которые нужны проверкам в worktree, например `["apps/api/.env"]`: git их в worktree не принесёт).
6. `/clear` или новая сессия — рельсы заработают.

## Режим 1: задача сейчас, вместе с агентом

1. Пишешь задачу своими словами. Агент вызывает `tw:spec`: вопросы по одному, файл `docs/specs/…md`, «Утверждаешь?».
2. После «да» — `tw:plan`: 2–7 задач с проверкой каждой, `docs/plans/…md`, «Утверждаешь план?».
3. После «да» агент исполняет план по задачам, отмечает `[x]` и пишет журнал.
4. Каждый раз, когда агент хочет остановиться после правок кода, Stop-hook гоняет конвейер и печатает строки `tw ▸` (правки только `.md` — спеки, планы, бэклог — конвейер не запускают):
   - проверки `check` — красные возвращают агента чинить (до 3 кругов, потом эскалация, потом человек);
   - scope — файлы вне плана или из «Не трогаем»;
   - независимый проверяющий — свежий агент сверяет спеку с diff по каждому пункту «Готово, когда».
5. `/tw:accept` — карточка одобрения: что сделано, вердикты, что проверить тебе, допущения, diff. «принято» → коммит после твоего «да»; «доработать» → агент продолжает.

## Режим 3: новый продукт или большая работа

1. `tw:spec` — спека продукта с тобой: цель, пользователи, сценарии, стек, что не делаем.
2. `tw:decompose` — эпики (срезы, которые можно потрогать; первый — каркас) и задачи под ними с полями «Эпик», «Область», «Зависит от». Утверждаешь одним списком.
3. `/tw:run` → выбираешь эпик: спеки и планы его задач агент пишет сам и показывает на одно утверждение; задачи встают в очередь.
4. Исполнитель гонит до трёх задач параллельно (области не пересекаются, зависимости выполнены); задача после проверок сама сливается в ветку эпика `tw/E1` — с проверками на результате слияния. В `main` без тебя ничего не попадает.
5. Все задачи эпика в ветке — уведомление «Эпик E1 готов к приёмке». `/tw:accept E1`: карточка эпика, как посмотреть, что проверить руками; «принять» — эпик в `main`; «доработать» — новая задача в том же эпике.
6. Следующий эпик — снова `/tw:run`.

## Режим 2: бэклог и исполнитель без тебя

1. Набрать задачи:
   - `tw:scout` — «собери бэклог», «что тут стоит сделать»: агент обходит проект и пишет `docs/backlog/B-NNN.md` с доказательствами;
   - `tw:task` — «запиши в бэклог …»: задача за секунды, без спеки.
2. `/tw:run`:
   - выбираешь задачи чекбоксами;
   - для каждой входящей — спека и план с тобой (задача S — быстрый путь: агент пишет их сам по тексту задачи и показывает на одно «утвердить / поправить / полный разговор»); после «да» они коммитятся в ветку задачи `tw/B-NNN` (не в `main`, твою ветку никто не переключает), задача становится `готова`;
   - режим: вся очередь или до N задач;
   - исполнитель стартует в фоне (`nohup`), сессию можно закрыть.
3. Исполнитель (`scripts/run.sh`) держит до `runWorkers` (по умолчанию 3) параллельных исполнителей, у каждого свой worktree (`.claude/worktrees/tw-run`, `tw-run-2`, `tw-run-3`). Задачу он отдаёт, когда её «Зависит от» приняты (или в эпике), а «Область» не пересекается с задачами в работе (нет поля — область берётся из файлов плана; нет и их — задача идёт одна). Переменные `runEnv` с `{slot}` получают номер исполнителя — так у каждого своя тестовая база и порты: `"runEnv": {"TEST_DATABASE_URL": "postgres://…/app_test_{slot}"}` (проект должен брать их из окружения). Каждый исполнитель с задачей: переходит на ветку `tw/B-NNN`, ставит зависимости (если поменялся lock-файл), запускает свежий `claude -p` по плану, тот же Stop-конвейер. Итог:
   - зелёные проверки и «да» проверяющего → коммит в ветку, `на приёмке`;
   - иначе → коммит `wip` в ветку, `застряла: <причина>`, берёт следующую;
   - два сбоя окружения подряд — стоп всего прогона; лимит five_hour ≥ 95 % — пауза до сброса;
   - второй исполнитель на тот же проект не запустится (`.claude/tw-state/run.pid`);
   - остановить: `bash <плагин>/scripts/run.sh stop` — незакоммиченное уходит `wip`-коммитом, задача возвращается в `готова` и остаётся первой в очереди.
4. Пока идёт прогон, в своей папке можно работать: исполнитель её не трогает. Общие у вас только Docker-контейнеры и база (`COMPOSE_PROJECT_NAME` = имя папки проекта).
5. Смотреть ход:
   - `/tw:run` открывает справа окно просмотра (`scripts/watch.sh`: Ghostty, iTerm2, tmux; в другом терминале — запусти сам): строки `run.log`, действия агента по текущей задаче со временем, строки `tw ▸`, итог задачи со стоимостью; каждый прогон начинается с чистого окна; прокрутка и поиск — как в обычном терминале;
   - весь разговор исполнителя по задаче — `claude --resume <сессия>` (команда в карточке `/tw:accept`): посмотреть и спросить, почему сделано так.
   - уведомления macOS: задача застряла и итог прогона (на приёмке / застряло / $ / минуты; та же строка `итог` в `run.log`); выключить — `"runNotify": false`;
   - окно просмотра показывает все потоки, строки с номером задачи;
   - модель исполнителя — `runModel` (по умолчанию `sonnet`); задача застряла не из-за решения человека — один повтор на `runEscalate` (по умолчанию `opus`, `""` — без повтора).
6. Итог — `/tw:status` (блок «Бэклог»: сделано / застряло / ждёт приёмки).
7. `/tw:accept` → список задач на приёмке → карточка по ветке против `main` → варианты (каждый — одна команда `scripts/accept.sh`):
   - принять и слить в `main` — `accept.sh merge B-NNN`: твоя папка должна стоять на `main` и быть чистой; перед слиянием `check` гоняется на результате слияния в `.claude/worktrees/tw-accept` — красное (две зелёные ветки вместе бывают красными) → `main` не меняется; выключить — `"acceptCheck": false` в `tw.json`; конфликт — `accept.sh rebase B-NNN`;
   - доработать — `accept.sh rework B-NNN "что не так"`: задача в плане ветки, статус `готова`, вернуть в очередь через `/tw:run`;
   - посмотреть UI — `accept.sh ui B-NNN` печатает команды для отдельного worktree ветки;
   - отклонить — `accept.sh reject B-NNN "почему"`, ветка остаётся.
8. Застрявшую задачу можно снова выбрать в `/tw:run`: продолжит в той же ветке, проверяющий увидит всю работу ветки, а не только последний кусок.

## Где смотреть, что пошло не так

| Файл | Что там |
|---|---|
| `.claude/tw-state/run.log` | события прогона |
| `.claude/tw-state/run/B-NNN-<время>.jsonl` | полный поток сессии исполнителя: действия агента, `tw ▸`, итог и стоимость |
| `.claude/tw-state/run/B-NNN.checks` | итог проверок задачи |
| `.claude/tw-state/run/B-NNN.verify` | вердикты проверяющего по пунктам с доказательствами |
| `.claude/worktrees/tw-run/.claude/tw-state/` | состояние hooks в worktree: `test.log`, `setup.log`, `install.log` |
| `.claude/tw-state/run.out` | ошибки самого исполнителя |

Worktree лежит в `.claude/worktrees/`: файлы под остальным `.claude/` Claude Code считает защищёнными и не даёт агенту их править. Путь исполнитель сам добавляет в `.git/info/exclude`. Убрать после прогонов: `git worktree remove .claude/worktrees/tw-run`.
| журнал плана в ветке `tw/B-NNN` | шаги исполнителя, «нужен человек: …» |
| `docs/backlog/B-NNN.md` | смены статуса |

`/tw:accept B-NNN` собирает это в одну карточку.

## Команды

| Команда | Что делает |
|---|---|
| `/tw:init` | подключить проект |
| `/tw:status` | pipeline, активные планы, бэклог, итог прогона |
| `/tw:run` | набрать задачи из бэклога и запустить исполнителя |
| `/tw:accept [B-NNN]` | приёмка плана или задачи бэклога |
| `bash <плагин>/scripts/watch.sh [open]` | просмотр хода исполнителя; `open` — в сплите справа |
| `tw:spec`, `tw:plan`, `tw:task`, `tw:scout`, `tw:estimate` | вызываются сами по смыслу просьбы |
